## 見やすさ（目視）

### 全体：矢印の向きが分からない

矢印の先の三角が、矢印の上の文字（ラベル）に重なって隠れているため、どちらを指しているか分からない箇所が多い。ラベルを矢印の先から離すか、線の途中に置いてほしい。

- 図01：ブラウザ → Next.js（「HTTPS」の文字が矢印にかぶっている）
- 図01：Next.js → Supabase Auth（「本人確認」の矢印の向きがない）
- 図01：pg_cron → Supabase DB（「限定RPC」の矢印が見えない）
- 図01：AI worker → Ollama（「ローカル」の矢印の向きが分からない）
- 図06：定期登録 → 内部API認証（「定期実行」の矢印の向きが切れている）
- 図07：queued → processing（「claim / lock」の矢印の向きがなく、文字が枠にかぶっている）
- 図07：done → 人の確認・修正（「採用前」の矢印が二重に見えて見づらい）
- 図07：矢印の上の文字が小さくて読みづらい

### レイアウト・文字の大きさ

- 図02：中段の4つの枠の中で、文字の上に隙間が空いているので、文字を上に詰めたほうが見やすい。
- 図03：上の5つの枠（プランナー、Next.js API など）の文字が左寄せになっているので、中央寄せにしてほしい。
- 図04：枠の中の文字が左に寄っていて右側が空いており、資料としての統一感がないので、中央寄せにしたほうがよい。
- 図08〜12（ER図）：枠の中の文字が小さすぎる。枠には余白が十分あるので、文字を大きくしてほしい。

### 用語

- 図02：下の「存在しない・不可視404」の「不可視」が言葉として伝わりづらい。「権限がなくて見られない場合も404にする（データがあるかどうかを教えないため）」など、分かる言葉にしてほしい。
- 図04：「宿題」が何を指すのか図だけでは分からない。「新郎新婦がプランナーに提出するもの（ゲスト名簿、席次表など）」と一言ほしい。
- 図04：「最新提出ポインタをRPCで競合制御」が難しい。英語の状態名（not_started など）と日本語が混ざっていて読みにくい。
- 図05：上の段（招待URLの状態）と下の段（ユーザーの状態）は別の話なのに横に並んでいて、つながっているように見える。枠で分けるなど区別してほしい。

## 内容（実装との対応）

1. 図07：左側の長い矢印が「done → 滞留回収」に見えるが、実際は「processing が30分を超えたとき（タイムアウト）→ 滞留回収」。矢印の出どころが違い、「タイムアウト」のラベルもない。
2. 図07：AIの出力が妥当でなかった場合の流れが分からない（人の確認・修正に行くように読める）。実際は、妥当でない出力は人に回さず、30分後に回収 → 3回未満なら queued に戻して再実行、3回目で failed（AIは利用不可の表示になり手動で継続）。「滞留回収 → queued（上限未満）」「人の確認・修正 → 採用 / 破棄」の矢印も PDF にない（編集用原本の .mmd にはある）。
   - 根拠：`worker/ai-worker.ts`、`supabase/migrations/20261009000200_system_monitoring.sql`
3. 図04：未着手・不備の宿題には、期限の7日前に「期限のご案内」（アプリ内通知）、期限を過ぎると「ご確認のお願い」（LINE、送れなければメール）が届くが、図に描かれていない。未着手から出る矢印が「免除」しかないため、提出しなくてもスタッフが免除するように見える。催促の通知（図06参照）を書き足してほしい。
   - 根拠：`src/app/api/internal/notifications-dispatch/route.ts`
4. 図04：「免除（対応不要）」は、プラン変更で不要になった宿題など特別な場合だけに使う（対応不要にできるのは未着手の宿題のみ）。その理由を書き、言葉を画面表示の「対応不要」に揃えてほしい。また「対応不要を解除 → 未着手」の矢印がない。
   - 根拠：`supabase/migrations/20260828001100_task_state_guards.sql`、`src/app/(staff)/cases/[caseId]/TaskSection.tsx`
5. 図05：invited に入ってくる矢印がない。実際は「管理者がスタッフを追加 → invited → パスワード設定 → active」、新郎新婦は「招待URLから登録 → そのまま active」。この2本の矢印を足してほしい。
   - 根拠：`src/app/api/admin/users/route.ts`、`src/app/api/auth/initial-register/route.ts`
6. 図05：「停止 → active（復帰）」の矢印がPDFにない（編集用原本の .mmd にはある）。また、削除は active だけでなく invited・停止中からもできるので、注記がほしい。
   - 根拠：`src/app/api/admin/users/[userId]/route.ts`
7. 図01：「pg_cron / GitHub Actions → Supabase DB（限定RPC）」となっているが、実際は pg_cron が共有secret付きで Next.js の内部APIを呼んでいる（GitHub Actions は死活確認のみ）。図06の「定期実行 → 内部API認証」と食い違っているので、図01を図06に合わせてほしい。
   - 根拠：`supabase/migrations/20260828001400_scheduled_jobs.sql`、`src/lib/api/internal.ts`、`.github/workflows/keepalive.yml`
8. 図02：編集用原本（02-画面遷移.mmd）では「権限不足 → P04 エラー画面」だが、実際（とPDF）は「その役割のホーム画面に戻す」。PDFは正しいが、原本から作り直したときに間違いが入るので原本を直してほしい。
   - 根拠：`src/lib/auth/session.ts` の `requirePageUser`

## 問題なしを確認したもの

- 図03：案件登録〜招待〜提出〜確認の流れと処理名は実装どおり。
- 図06：LINEは期限切れ・不備の重要通知だけに使い、それ以外や上限超えはメールに切り替える流れは実装どおり。
- 図07：AI worker の30秒ごとの取得、30分で回収、3回まで再試行、心拍10分で利用不可の表示は実装どおり。
- 図08〜12（ER図）：外部キーの関係54本すべて、多重度（1対1・1対多・任意）が [schema.json](schema.json) のDB定義と一致。設計図の作成後にDB定義（migration）の変更はない。
