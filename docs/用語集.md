# にこまる 用語集

システム開発や作業のやり取りでよく出てくる「初心者には難解な言葉」を、専門知識がなくてもイメージできるようにやさしく解説したページです。

**使い方**

- 分からない言葉が増えたら、そのつどこのページに追記してください。
- ここに無い言葉があったら、そのまま Issue（連絡掲示板）にコメントで質問してください。質問したこと自体が、次に追加すべき項目の候補になります。
- 完璧である必要はありません。書いてあることのほうが大事です。

## RLS（データのお部屋ごとの鍵 / Row Level Security）

**「このデータは誰が見て・書いていいか」を、データベース自身が判断して守る仕組み**です。

**なぜ大事？**
画面側で「この人には非表示」と設定しても、プログラムの書き忘れがあると情報が漏れてしまいます。データベース自体に鍵をかけておけば、プログラムを間違えても情報は漏れません。「にこまる」では、これを安全を守る**一番最後の砦**として使っています。

**かみくだいたポイント**
- **鍵の種類は2つ**: 「どれか1つの条件を満たせばOK（足し算）」と、「すべての条件を満たさないとダメ（掛け算）」という2種類の鍵のかけ方があります。
- **設定の組み合わせに注意**: 足し算タイプのルールを適当に作ると、関係のない人までデータを見たり書き込めたりしてしまう危険があります。しっかりルールを揃えて防ぎます。
- **ルール同士がケンカしないように**: データがお互いのルールを無限に呼び出し合うとエラーで画面が止まります。そうならないよう、確認専用の安全な道（関数）を通すようにしています。

**関連**: `supabase/migrations/20260828000500_rls_policies.sql`, [README.md](../README.md) の「設計上の要点」, `tests/db/`（RLSテスト。PGlite 上で毎回機械検証している）

## マイグレーション（データベースの設計図・更新レシピ）

**データベースの作り方や更新手順を、毎回同じ状態に再現できるように順番に記した手順書（ファイル）**です。

**なぜ大事？**
自分のパソコンで動くシステムと、本番用のシステムでデータベースの形がズレているとエラーの原因になります。手順書を古い順にひとつずつ実行することで、**誰の環境でも全く同じデータベース**を積み上げて作ることができます。

**かみくだいたポイント**
- 手順書は日付順に並んでいて、上から順番に実行されます。
- 新しいデータの部屋（テーブル）を追加したときは、「誰に操作を許すか」という権限もセットで追加しないと「アクセス権がありません」と怒られて動かなくなります。

**関連**: `supabase/migrations/`

## PostgREST（データベースを直接つなぐ自動窓口）

**データベースの中身を、Webサイトやアプリから直接操作できるように勝手に窓口を作ってくれる仕組み**です。

**なぜ大事？**
普通は「データベースとやり取りするための受け付け窓口」を人間がイチから作りますが、この仕組みを使えば自動で窓口ができます。データベース側のルール（RLS）がそのまま窓口のルールになるため、安全面でも管理が楽になります。

**かみくだいたポイント**
- **検索の記号に注意**: 検索窓に「,（カンマ）」や「( )（カッコ）」を入れると仕組みがカンチガイしてバグるため、記号を安全な文字に変える処理（エスケープ）をしています。

**関連**: `src/lib/errors.ts`（PostgREST のエラーを表6-の形式へ変換）, `src/lib/services/users.ts`

## Server Component / Client Component（画面の表示分担）

Next.jsという仕組みで画面を作るとき、**「サーバー側で準備するか」「使う人のブラウザで動かすか」という役割分担**のことです。

- **Server Component（サーバー担当）**: サーバー側で画面を完成させてから届ける仕組み。使う人のスマホやPCの負担が減り、表示が速くなります。**基本はこちらを使います。**
- **Client Component（ブラウザ担当）**: 画面を開いた後、ボタンを押したり文字を入力したり「使う人の操作に合わせて動く」仕組み。必要な場所だけに絞って使います。

**なぜ大事？**
「とりあえず全部ブラウザ担当で動かせばいいや」とすると、スマホ側の処理が重くなり、画面が開くのが遅くなってしまいます。

**関連**: `src/app/(couple)/mypage/tasks/[taskId]/SubmitForm.tsx` など、ファイル先頭に `'use client';` があるもの

## CI（自動品質チェックロボット / 継続的インテグレーション）

プログラムの変更を出したときに、**「エラーや崩れがないか」をロボットが自動でテストしてくれる仕組み**です。

**なぜ大事？**
人間がいちいち手作業でチェックしなくても、壊れたプログラムが混ざるのを自動で防いでくれます。チェック画面で「緑のマーク（OK）」か「赤のマーク（ダメ）」かがひと目で分かります。

**かみくだいたポイント**
- 「にこまる」の自動チェックでは、プログラムの書き方チェック・動作テスト・セキュリティ（変なパスワードが紛れ込んでいないかなど）をまとめて確認しています。
- PRを提出する前に自分のPCでチェックを実行しておくと、自動テストで引っかかるのを防げます。

**関連**: `.github/workflows/ci.yml`, [開発のはじめかた.md](開発のはじめかた.md) の「コードを書く人だけ、出す前に」

## E2Eテスト（通しでの実動作テスト / End to End）

部品ごとではなく、**「実際のユーザーと同じように画面をポチポチ操作して、最後まで動くか」を確かめるテスト**です。

**なぜ大事？**
細かい部品が正しく作られていても、全部をつなぎ合わせたときに「ボタンが押せない」「次の画面に進まない」といった問題が起きることがあります。それを防ぐため、ロボットが代わりに画面を自動操作して「ログインから提出まで」の一連の流れを確認します。

**関連**: `playwright.config.ts`, Issue #19

## pg_dump（データベースの丸ごとバックアップ）

**データベースの中に残っているすべてのデータを、丸ごと1つのファイルに書き出すコマンド**です。

**なぜ大事？**
システムを新しくしたり、大きな作業をしたりする前に実行しておけば、「万が一データが壊れても元の状態に戻せる」という安心安全のための保険になります。

**関連**: Issue #22

## SPF / DKIM（メールの「本物証明書」セット）

届いたメールが「なりすましではなく、本当に『にこまる』から送られたものか」を受信側（Gmailなど）が確かめるための仕組みです。

- **SPF**: 「このサーバーから送るメールは本物です」とあらかじめリスト登録しておく仕組み。
- **DKIM**: メールに見えない「電子スタンプ」を押し、途中で内容が書き換えられていないか確かめる仕組み。

**なぜ大事？**
この設定をしていないと、大事なログインメールや通知メールが**勝手に「迷惑メールフォルダ」に入ってしまったり、届かなくなったりします**。

**関連**: [TASKS.md](../TASKS.md)（「認証メール用の独自ドメイン取得と SPF／DKIM」）, Issue #17

## ワーカー（裏で黙々と働く専門スタッフ / worker）

Webサイトの画面とは別に、**裏側の別のパソコンでずっと待機して、時間がかかる仕事（AI処理など）を専門でこなすプログラム**です。

**なぜ大事？**
AIの回答作成には時間がかかるため、通常の画面処理と一緒に動かすとエラーで止まってしまいます。そのため「画面」と「AIの計算」を別々に分け、「GPU（グラフィックカード）を載せた専用のマシン」に作業を任せています。アプリ側が頼みに行くのではなく、ワーカー側が「何かやることある？」と30秒ごとに見に来る仕組みにすることで、セキュリティも高めています。

**かみくだいたポイント**
- **乗っ取られても安全に**: 万が一このスタッフ（ワーカー）が悪意ある人に乗っ取られても、大切なデータを全部盗まれないよう、必要最低限の作業（タスク確認と結果入力）しかできない専用の鍵を渡しています。
- **複数人で分担OK**: ワーカーを何台同時に動かしても、作業を横取りし合わない仕組み（取り合い防止のロック機能）が入っています。
- **定期的な「生存確認」**: ワーカーからの返答（心拍）が10分間途絶えたら、画面側で自動的に「AI機能は使えません」と表示を切り替え、手動で作業できるようにバックアップします。

**関連**: `worker/ai-worker.ts`, `scripts/setup-ai-e2e.mts`, Issue #22

## 冪等（べきとう / 何度やっても同じ結果になる安心設計）

ボタンを何回連打しても、システムのエラーで同じ送信が繰り返されても、**「1回だけ実行したときと結果が変わらない」という性質**のことです。


**なぜ大事？**
電波が不安定でボタンを2回押してしまった、画面が固まって連打した……といった事故は日常茶飯事です。もしこれが「商品注文」で冪等になっていないと、連打した分だけ二重注文されたり二重決済されたりします。冪等にしておくことで、**何度重複して処理が飛んできてもデータが壊れない安全なシステム**になります。

**仕組みの実例**
- **データ登録（insert）**: すでに同じデータがある場合は、「エラーにせず無視する」か「上書きする」ルールにしておきます。
- **宿題の提出（6-7）**: 同じ宿題に2回提出ボタンを押しても、新しいデータが増えるのではなく「1回目の提出内容を最新版に上書きする」動きになります。
- **通知の受信（6-10）**: LINEから同じ通知が2回届いても、2回目は「受信済み」と判断してスルーします。

**関連**: `supabase/seed.sql`, `supabase/migrations/20260828001000_submission_sharing.sql`, `src/app/api/tasks/[taskId]/submit/route.ts`, 基本設計書 6-7「業務ロジック：提出物確認と提出の冪等性」
