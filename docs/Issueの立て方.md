# Issueの立て方

Issue を「短く読めて、すぐ着手できる」状態に保つためのルールです。
Issue を探す人・立てる人・PR を出す人の全員が対象です。

## 今やるIssueを探す

Issues タブを普通に開くと、待ちのものもまとめて表示されます。**下のリンクから開いてください。**
同じリンクを、Issues タブの一番上にピン留めした Issue にも置いています。

| 見たいもの                               | リンク                                                                                                                                                                            |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **今すぐ着手できるIssue（担当者なし）**  | [開く](https://github.com/ryuki-moro/Nicomaru/issues?q=is%3Aissue%20state%3Aopen%20-is%3Ablocked%20-label%3A%E6%B1%BA%E5%AE%9A%E5%BE%85%E3%81%A1%20-label%3Aepic%20no%3Aassignee) |
| 自分が担当しているIssue                  | [開く](https://github.com/ryuki-moro/Nicomaru/issues?q=is%3Aissue%20state%3Aopen%20assignee%3A%40me)                                                                              |
| 待ちのIssue（先に終わらせるものがある）  | [開く](https://github.com/ryuki-moro/Nicomaru/issues?q=is%3Aissue%20state%3Aopen%20is%3Ablocked)                                                                                  |
| 決定待ちのIssue（人の判断を待っている）  | [開く](https://github.com/ryuki-moro/Nicomaru/issues?q=is%3Aissue%20state%3Aopen%20label%3A%E6%B1%BA%E5%AE%9A%E5%BE%85%E3%81%A1)                                                  |
| 将来候補（学校制作の範囲外。閉じてある） | [開く](https://github.com/ryuki-moro/Nicomaru/issues?q=is%3Aissue%20label%3A%E5%B0%86%E6%9D%A5%E5%80%99%E8%A3%9C)                                                                 |

## 1 Issue = PR 1本

Issue は次の大きさにそろえます。

- **PR 1本・2日以内で終わる**
- **終わりの条件は3つまで**（4つ以上あるなら分ける）
- **タイトルは「〜する」で終わる30字前後**。タイトルだけで何をするか分かるようにする
- 長い手順・背景・調査結果は `docs/` に書いて、Issue にはリンクだけ置く

| よくない例                                           | よい例                                                                                                    |
| ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 「発表・検証用環境を整える」（作業が10個ある）       | 親「発表・検証用環境を整える」＋子「Supabaseのデモ用プロジェクトを作る」「LINEのテスト用チャネルを作る」… |
| 「E2Eテスト」                                        | 「招待から初回登録までのE2Eテストを書く」                                                                 |
| 本文が手順書になっていて、終わりの条件が埋もれている | 「なぜやるか」2行＋「終わりの条件」3つ＋手順書へのリンク                                                  |

大きい作業は **「まとめ（親Issue）」を立てて、子Issueに分けます。**
親Issueの本文の下にある **Create sub-issue** から子Issueを作ると、親に進み具合（例: 2/5）が表示されます。
親Issue自体では作業しません（`epic` ラベルが付き、「今すぐ着手できるIssue」には出ません）。

## Issueの立て方

`New issue` を押すと、3つの形式から選びます。白紙のIssueは作れません。

| 形式              | 使うとき                                                       |
| ----------------- | -------------------------------------------------------------- |
| 作業              | PR 1本で終わる作業。コード・資料・手作業のどれでもこれを使う   |
| まとめ（親Issue） | PRが2本以上・2日を超える作業。作ったあと子Issueに分ける        |
| 不具合            | 同じ操作で誰でも再現できる不具合（試験で見つかったものを含む） |

「作業」で選んだ **種類** と **Agent AI** は、自動でラベルになります。

## 待ち・決定待ち・将来候補

今は着手できない Issue は、次のどれかにして「今すぐ着手できるIssue」から外します。

| 状態     | やり方                                                                                                                                             | 戻るとき                                                                |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| 待ち     | 「作業」の **先に終わっている必要があるIssue** に `#12` のように書く。あとから足すときは、右側の **Relationships** → **Mark as blocked by** で選ぶ | 相手のIssueが閉じると自動で一覧に戻り、「着手できます」とコメントが付く |
| 決定待ち | `決定待ち` ラベルを付け、本文に「誰の・何の判断を待っているか」を1行書く                                                                           | 決まったらラベルを外す                                                  |
| 将来候補 | `将来候補` ラベルを付ける。**自動で「対応しない」として閉じます**                                                                                  | やると決まったら再オープンする（ラベルは自動で外れる）                  |

> 「12月になったらやる」のように時期を待つ作業は、前の工程の Issue を「待ち」に登録します。
> 月の目安はマイルストーン（例: `2026-12 学校成果物`）で表します。

## ラベル

| 分け方   | ラベル                           | 付け方                                 |
| -------- | -------------------------------- | -------------------------------------- |
| 種類     | `コード` `資料` `手作業` `bug`   | 「作業」「不具合」の形式から自動       |
| Agent AI | `Agent AI不要` `Codex使用可`     | 「作業」の形式から自動                 |
| 難しさ   | `かんたん` `ふつう` `むずかしい` | 手で付ける（任意）                     |
| 状態     | `決定待ち` `将来候補`            | 手で付ける（上の表を参照）             |
| まとめ   | `epic`                           | 「まとめ（親Issue）」の形式から自動    |
| 学校     | `学校成果物`                     | 学校に提出・発表する成果物に手で付ける |

## Pull Request のルール

- **PR 1本で閉じる Issue は1つだけ。** 本文の `Closes #番号` に1つだけ書きます
- PR が大きくなりそうなら、先に Issue を分けてから PR も分けます
- 書き方は PR を作ると出てくるテンプレートに従います（やったこと・確かめたこと・AIを使わずに確かめる手順）

### 依存関係の自動更新PR（Dependabot）

部品（npm パッケージ・GitHub Actions）の更新は Dependabot が自動で PR を作ります。PR が増えすぎないよう、次の形にしています。

- **毎月1日に、npm で1本・GitHub Actions で1本**（最大2本）にまとめて届く
- npm の**メジャー更新（例: 22.x → 26.x）は届かない**。互換性の確認が要るので、必要になったら「作業」Issue を立てて手で上げる
- **脆弱性を直すセキュリティ更新は別枠で、見つかりしだい届く**
- CI が通ればマージしてよい。特定のパッケージで CI が落ちる場合は、PR に `@dependabot ignore パッケージ名` とコメントすると、そのパッケージを除いて作り直される

設定は [.github/dependabot.yml](../.github/dependabot.yml) にあります。
