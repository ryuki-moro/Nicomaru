## 総評

25テーブルのデータ設計、RLS の permissive／restrictive 結合まで踏み込んだ認可設計、無料枠の制約を起点にした技術選定、AI駆動開発を前提にしたレビュー統制（12-2）と、学生の卒業制作としては明らかに水準が高い。とくに13章で未確定事項を着手ブロッカー付きで自己申告した点、Service Role Key の使用範囲を表で縛りPRルールに落とした点は、実務の設計書でも珍しい丁寧さ。弱点は一貫して「書いた仕様を最後まで通していない」ところに集中している。付録AのRLSは相互再帰して初回実行で落ち、update／delete系ポリシーは丸ごと先送り、couple_profiles は誰が作るのかが章で食い違い、招待URLは発行しても表示する画面が無く、提出形式の値域は3箇所で違う。表・画面・APIのいずれか1つに定義があれば残り2つが欠けているという型の欠落が、Phase 1 の中心導線（案件登録→招待→初回登録→提出→確認）に集中しているのが最大の問題。設計の考え方と粒度の判断は良いが、Phase 1 を通しで実装できる状態にはまだない。

## 承認判断

差し戻しではなく条件付き承認。設計方針そのものに作り直しを要する誤りは無く、指摘の大半は追記・統一・カラム追加で解消する。ただし rank 1〜10（RLS相互再帰、DMLポリシー欠落による権限昇格、couple_profiles の作成主体、招待URLの導線と検証、提出形式、利用者管理API、assign-tasks 仕様、リスク算出式）は Phase 1 の骨格であり、未修正のまま着手すると確実に作り直しになる。この10件の改訂と、13章の合意必須のうち「ワンタイム認証の採用」「招待トークン有効期限」の合意をもって Phase 1 着手可とする。

## 評価できる点

- RLS の permissive／restrictive 結合仕様（permissive 同士は OR、restrictive は AND）を 6-3-4 で明示し、論理削除除外を as restrictive で実装する SQL を付録Aに残している。学生チームの基本設計書でここまで踏み込んだ例は稀で、「アーカイブ済み案件が見えてしまう」という頻出事故を1つ確実に潰している。
- Service Role Key の使用箇所を表48 で3経路に限定し、それぞれに「RLSバイパス時に何を検証するか」を書いたうえで、12-2 で「使用範囲表にない新規使用はPRで表の更新を伴わない限り却下」とプロセスに落としている。AI駆動開発でRLSエラーを Service Role で回避する典型的な失敗を、文書とレビュー規約の両方で塞ぐ構成。
- 13章で未確定事項17件を1箇所に集約し、「合意必須（着手ブロッカー）／仮決めで進行可」の優先度と、未確定が実装のどこを止めるかまで書いている。ワンタイム認証を「要件との差異」として自ら申告している姿勢も含め、そのまま合意会議の議題にできる。
- 2-2-1 と表6 の代替案検討が良質。Firebase／自前バックエンド／ORM／Redisキュー／外部監視SaaS／クラウドLLM を不採用理由付きで整理し、Vercel Hobby の制約からスケジューラを pg_cron へ、PDF生成をブラウザ印刷へ、AIジョブをプル型へ確定している。制約起点で構成を決めた過程が第三者に追える。
- 5-2 のテーブル一覧（25テーブル）と 5-3 のカラム定義が掲載順まで含めて過不足なく1対1で対応している。risk_score_snapshots の is_current を部分ユニークインデックスで担保すると実装方法まで書き切っている点も、DDL作成者が迷わない水準。

- DB値とUI表示名の対応を表53 に一元化し、12-2 で「定数モジュールとして単一ソース化し、AIが画面ごとに独自の表示名を発明することを防ぐ」と実装統制まで結び付けている。プロンプトを ai_prompt_templates でDB管理する設計も含め、保守性要求を具体的なテーブル設計に落とせている。
- 章をまたいだ委譲が空手形になっていない。3-3-2「トランザクション境界・冪等性は第6章 6-6 に定義」に対し 6-6-2 がAPI分割・中間状態の扱い・自動リトライ禁止まで具体化しており、同一内容を複数章に重複記述して食い違わせるという設計書で最も起きやすい破綻を構造的に避けている。

## 指摘詳細

### #1 [重要] RLSポリシーが相互再帰し、couple・plannerの主要画面が実行時エラーになる

**該当箇所**: 付録A couple_profiles_select（1494-1508行）・cases_select_couple（1513-1520行）・case_tasks_select（1553-1566行）・task_submissions_select（1570-1584行）／6-3-4（1058行）／付録A末尾（1585行）

**内容**

couple_profiles_select が wedding_cases を参照し（1501行）、wedding_cases の cases_select_couple が couple_profiles を参照する（1516行）。PostgreSQL はポリシー式中で参照した他テーブルにもRLSを適用するため両者が相互展開され、42P17 infinite recursion detected in policy で失敗する。case_tasks_select（1560行）と task_submissions_select（1578行）も同じ couple_profiles→wedding_cases 経路を内包しており同様。1058行と1585行は security definer 関数を「ポリシー間の重複削減・保守性」目的としか位置づけておらず、例示も is_admin_of()／is_system_admin() の2つで、再帰の主因である couple→case 解決が入っていない。設計どおり実装すると Phase 1 の M01〜M04・K01・K02 が初回実行で落ちる。

**修正案**

6-3-4 に「RLS共通関数」の項を新設し、付録AのSQLを書き換える。(1) current_app_user()（security definer / stable / set search_path = public, pg_temp）で auth.uid() から id・role・venue_id・status を解決。(2) my_case_ids() で couple の case_id 集合を解決し、ポリシー式から couple_profiles・wedding_cases への直接参照を排除。(3) 両関数の EXECUTE は authenticated のみに付与。(4) 付録Aの5ポリシーをこの関数呼び出しに統一。(5) 6-3-4 の文言を「security definer 関数は保守性のためではなく再帰回避のため必須」に改める。(6) 11章 表64 のRLSテストに「各ロール×各テーブルの select で 42P17 が発生しないこと」を追加。

### #2 [重要] 新郎新婦氏名の保存先と couple_profiles の作成主体が章間で矛盾

**該当箇所**: 3-3-2（206-216行）／3-3-1（198-204行）／6-6-1 手順5（1151行）／表13 K03（360-369行）／表21（525-542行）／表22（547-562行）

**内容**

K03 は新郎氏名・新婦氏名を必須入力させるが、wedding_cases（表21）に氏名列は無く、置き場は couple_profiles.full_name のみ。ところが 3-3-2 の処理内容は wedding_cases／case_invitations／case_tasks／timeline_items の作成しか列挙せず couple_profiles を作らない。一方 3-3-1 と 6-6-1 手順5 は初回登録時に「user_profiles（role=couple）／couple_profiles を作成し」と新規作成を規定する。案件登録時に作れば二重作成、作らなければ招待前の K01「カップル名」・K02「新郎新婦氏名」が表示できない。表22 には UNIQUE(case_id, partner_role) も UNIQUE(user_profile_id) も無く重複を止める制約が一切ない。表22 の user_profile_id が「未招待・共有時はNULL可」であることから案件登録時作成が設計意図と読めるが、本文がそれを書いていない。

**修正案**

6-6-1 を「案件登録時に couple_profiles を partner_role ごとに2行作成（user_profile_id は NULL、連絡先入力側に is_primary_contact=true）／初回登録は case_invitations.target_partner_role で対象行を特定し user_profile_id・メールを UPDATE」に確定する。3-3-2 の処理内容に couple_profiles 作成の1行を追加し、3-3-1 と 6-6-1 手順5 の「作成」を「特定して更新」に修正。表22 に UNIQUE(case_id, partner_role) と UNIQUE(user_profile_id)（NULL可）を追加。表23 の target_partner_role を NOT NULL 化して partner_role の決定源を確定。P02 の氏名がプランナー入力値を上書きするのか併記するのかも 6-6-1 に明記。

### #3 [重要] 招待トークンと登録メールが未照合。失効チェック漏れとトークン消費の非原子性も残る

**該当箇所**: 6-3-1（1010行）／表11 P02（312-319行）／3-3-1（198-204行）／表23 recipient_email（572行）／表48 initial-register 行（1065行）／6-6-1 手順5-6（1151-1152行）

**内容**
