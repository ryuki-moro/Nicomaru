# テスト技法・観点と実装の対応

Issue [#56](https://github.com/ryuki-moro/Nicomaru/issues/56) のレビュー用資料です。現行コードの試験を根拠にした選定案です。授業資料・学校の指定用語は未共有のため、授業内容との一致はメンバーが確認してください。[試験仕様書](テスト仕様書_校内デモ.xlsx)にはケースごとの技法・入力・期待結果を記載しています。

## 選び方

| 技法・観点         | このアプリで調べること                                                                | 選ぶ理由                                                         | 自動試験の根拠                                                                                |
| ------------------ | ------------------------------------------------------------------------------------- | ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 同値分割           | 正しい日付、存在しない日付、書式違い、空欄、重複パラメータ                            | 入力の種類ごとに結果が異なるため、それぞれを代表する値で確かめる | `tests/unit/notification-log-period.test.ts`、`pagination.test.ts`                            |
| 境界値             | 招待期限の直前・同時刻・直後、使用回数の上限、CSV終了日の翌日0時、監査保持の2暦年境界 | 比較演算の誤りで1件余分に許可/拒否する不具合を検出する           | `tests/unit/invitations.test.ts`、`notification-log-period.test.ts`、`tests/db/audit.test.ts` |
| デシジョンテーブル | ロール、利用者状態、同じ式場/別式場、担当/非担当と許可操作の組合せ                    | 画面が見えることと更新できることを分け、権限の抜けを検出する     | `tests/db/rls.test.ts`、`rls-submission.test.ts`、`venue-permissions.test.ts`                 |
| 状態遷移           | 下書き→提出→不備→再提出→確認、対応不要、招待の失効、AIの処理→人の採用                 | 単発の入力が正しくても、前の状態によって拒否すべき更新がある     | `tests/db/case-task-state.test.ts`、`ai-jobs.test.ts`、`tests/e2e/core-flow.spec.ts`          |
| 組合せ             | 4ロールと利用者状態、PC/スマートフォン寸法、通知経路と失敗の組合せ                    | 重要な相互作用を落とさない。権限境界は組合せを省略しない         | `tests/unit/session.test.ts`、`tests/db/notifications.test.ts`、`playwright.config.ts`        |
| 同時実行           | 同じ招待の同時消費、採番、レート制限、同じ提出の同時確認                              | 順番に成功するだけでは競合時の整合性を証明できない               | `tests/db/concurrency.test.ts`（専用PostgreSQL）                                              |
| 失敗注入・回復     | Storage削除、DB更新、監査応答の失敗/停止、APIの不正本文                               | 途中失敗を成功と誤記せず、再操作できることを確かめる             | `tests/unit/case-purge.test.ts`、`password-auth.test.ts`、`api-client.test.ts`                |
| 負例による退行検知 | Service Workerの`no-store`を隔離プロキシで変更した場合に既存E2Eが失敗するか           | 成功するだけでなく、対象の不具合を検出できる試験であると確認する | [実行記録](../検証/自走完了_20261009.md)                                                      |

表中の省略したファイル名は、その行で先に記載したディレクトリと同じです。組合せ試験は全体をペアワイズ網羅したという意味ではありません。必要な組合せを明示して試験しています。

## ケースを具体化する例

| 前提                                          | 入力・操作                         | 期待結果                           | 技法             |
| --------------------------------------------- | ---------------------------------- | ---------------------------------- | ---------------- |
| 有効期限が2026-09-01 00:00:00 UTCの未使用招待 | 現在時刻を同時刻に固定して状態判定 | `expired`になる                    | 境界値           |
| 初回登録用の新しい招待                        | 期限・使用上限を取得               | 発行から14日、使用は1回            | 同値分割・境界値 |
| 通知CSVの期間フォーム                         | 2026-02-30を開始日に指定           | `from`の項目エラー、HTTP 400       | 同値分割         |
| 提出済み宿題                                  | plannerが「対応不要」に変更        | 更新を拒否し提出実績を保持         | 状態遷移         |
| 同一の有効な1回限り招待                       | 独立した2つのDB接続で同時に消費    | 成功は1回だけ                      | 同時実行         |
| Authでパスワード更新が成功                    | 続く監査RPCが応答しない            | 待ち時間を打ち切り、更新成功を維持 | 失敗注入・回復   |

時刻境界・保持期限・削除の試験は、固定時刻/模擬DBで行います。共有デモ環境の日付や実データを変更して再現しません。メールはローカルの受け口、LINEとAI推論は模擬結果を使う自動試験と、実サービス/実LLMの人による確認を区別します。

## メンバーによるレビュー

1. 授業資料の用語とこの表の技法を照合し、学校指定があれば注記します。
2. 試験仕様書から担当機能の正常系と異常系を1件ずつ選び、前提・手順・期待結果が一意に分かるか読みます。
3. 隣のメンバーがAgent AIなしで実行し、曖昧な手順を記録します。担当、対象commit、環境、実施結果を記入します。
4. 不足は試験IDを付けて追記し、実装変更が必要なものは不具合Issueへ結び付けます。
5. 「その値を選んだ理由」「許可すべき場合と拒否すべき場合」「試験しなかった範囲」を自分の言葉で説明します。

成功件数、カバレッジ、ブラウザー試験は[検証記録](../検証/自走完了_20261009.md)の対象版を参照します。コードの分岐網羅100%は指定した3モジュールの測定であり、全機能・学校の受入試験・実端末の合格ではありません。
