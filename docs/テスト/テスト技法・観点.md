## ケースを具体化する例

| 前提                                          | 入力・操作                         | 期待結果                           | 技法             |
| --------------------------------------------- | ---------------------------------- | ---------------------------------- | ---------------- |
| 有効期限が2026-09-01 00:00:00 UTCの未使用招待 | 現在時刻を同時刻に固定して状態判定 | `expired`になる                    | 境界値           |
| 初回登録用の新しい招待                        | 期限・使用上限を取得               | 発行から14日、使用は1回            | 同値分割・境界値 |
| 通知CSVの期間フォーム                         | 2026-02-30を開始日に指定           | `from`の項目エラー、HTTP 400       | 同値分割         |
| 提出済み宿題                                  | plannerが「対応不要」に変更        | 更新を拒否し提出実績を保持         | 状態遷移         |
| 同一の有効な1回限り招待                       | 独立した2つのDB接続で同時に消費    | 成功は1回だけ                      | 同時実行         |
| Authでパスワード更新が成功                    | 続く監査RPCが応答しない            | 待ち時間を打ち切り、更新成功を維持 | 失敗注入・回復   |

時刻境界・保持期限・削除の試験は、固定時刻/模擬DBで行います。共有デモ環境の日付や実データを変更して再現しません。メールはローカルの受け口、LINEとAI推論は模擬結果を使う自動試験と、実サービス/実LLMの人による確認を区別します。

## 5技法の使い分けと選定理由（レビュー案）

照合対象: `905ff30f57b2dcea66f85e9784f919615cc81214`。以下は実装・既存自動試験を読んで整理した説明案です。本人の説明や授業資料の確認、実装担当者の承認を代行した記録ではありません。

| 判断したいこと                     | 選ぶ技法           | このアプリで選ぶ理由                                                                   |
| ---------------------------------- | ------------------ | -------------------------------------------------------------------------------------- |
| 入力の種類で処理が分かれるか       | 同値分割           | ページ番号の文字列、空欄、配列を分けると、同じ処理になる入力を整理して代表値を選べる   |
| 許可と拒否が切り替わる値はどこか   | 境界値分析         | 招待期限の `<=` を `<` に誤ると、期限ちょうどだけ判定が変わるため                      |
| 複数条件から結果が決まるか         | デシジョンテーブル | 招待の失効・使用済み・期限切れが同時に成立するときの優先順位を明示できる               |
| 前の状態と操作で次の状態が変わるか | 状態遷移           | 提出済み宿題を対応不要にすると提出実績が消えるため、拒否と状態保持を確認する必要がある |
| 複数因子の相互作用を確かめたいか   | 組合せ             | ロール・利用者状態・対象式場などが同時に効くため。権限に関わる組合せは削減せず列挙する |

同値分割の代表値だけでは境界の比較誤りを拾えないので境界値分析を追加します。デシジョンテーブルは同時に成立する条件と結果、状態遷移は操作前後の状態を整理します。組合せは因子の相互作用を見る方法で、すべてをペアワイズへ削減するという意味ではありません。

### 同値分割: 一覧ページ番号

`src/lib/pagination.ts` の `resolvePage` と `tests/unit/pagination.test.ts` を照合しました。

| クラス                       | 代表入力                           | 期待結果  |
| ---------------------------- | ---------------------------------- | --------- |
| 上限以内の正の10進整数文字列 | `'2'`                              | 2ページ目 |
| 数字以外を含む文字列         | `'2abc'`                           | 1ページ目 |
| 欠落・空欄                   | `undefined`、`''`                  | 1ページ目 |
| 配列（重複指定を含む）       | `['2', '3']`                       | 1ページ目 |
| 範囲外                       | `'0'`、`String(MAX_LIST_PAGE + 1)` | 1ページ目 |

異常入力を常にHTTP 400にするわけではありません。この関数では1ページ目へ補正します。通知期間の不正日付と同じ期待結果へまとめないことが要点です。

### 境界値: 招待期限

`src/lib/services/invitations.ts` の `invitationState` は `expires_at <= now` で期限切れとします。失効なし・未使用・使用回数0/上限1、期限Tを固定したケースです。

| 現在時刻     | 期待状態  |
| ------------ | --------- |
| Tの1ミリ秒前 | `unused`  |
| Tちょうど    | `expired` |
| Tの1ミリ秒後 | `expired` |

この3点はレビュー用の設計例です。既存 `tests/unit/invitations.test.ts` には期限内・期限切れ・同時刻の試験がありますが、上記の±1ミリ秒3点がそのまま実装済みとは扱いません。初回招待の「14日・1回」は仕様値の確認であり、それだけで境界値網羅にはなりません。

### デシジョンテーブル: 招待状態の優先順位

同じ `invitationState` の分岐を表にします。使用済み条件は `used_at` がある、または `use_count >= max_uses` です。「—」は結果に影響しない条件です。

| 条件/結果            | D1        | D2     | D3        | D4       |
| -------------------- | --------- | ------ | --------- | -------- |
| `revoked_at` がある  | はい      | いいえ | いいえ    | いいえ   |
| 使用済み条件を満たす | —         | はい   | いいえ    | いいえ   |
| 期限切れ             | —         | —      | はい      | いいえ   |
| 期待状態             | `revoked` | `used` | `expired` | `unused` |

失効と使用済みが重なったら `revoked` を優先します。既存試験はこの重なりを確認しています。各列は分岐規則を整理したもので、全条件の真偽8通りを実行したとの主張ではありません。

### 状態遷移: 対応不要の付与・解除

`supabase/migrations/20260828001100_task_state_guards.sql` と `tests/db/case-task-state.test.ts` の対応です。担当plannerなど認可済みの利用者を前提とし、認可試験は別に行います。

| 操作前                                  | 操作            | 期待する操作後/結果          |
| --------------------------------------- | --------------- | ---------------------------- |
| `not_started`                           | `waived: true`  | `waived`                     |
| `waived`                                | `waived: true`  | `waived`（再送を受け付ける） |
| `waived`                                | `waived: false` | `not_started`                |
| `submitted` / `needs_fix` / `confirmed` | `waived: true`  | `BH422`、元の状態を保持      |
| `submitted` / `confirmed`               | `waived: false` | `BH422`、元の状態を保持      |
| `confirmed`                             | 期限だけ更新    | `confirmed`を保持            |

成功経路に加えて禁止遷移を確認する理由は、エラーが出るだけでは実績の保護を証明できないためです。更新後の状態も検査します。この表は宿題全体の遷移網羅表ではなく、対応不要操作に絞ったものです。

### 組合せ: 式場更新権限

`tests/db/venue-permissions.test.ts` には system_admin の更新成功と、admin・planner・couple・別式場admin・停止planner・未認証の更新拒否があります。拒否時は更新行数0と式場名が保持されることを確認しています。

この試験から「4ロール×全利用者状態×全式場の直積を網羅した」とは言えません。上記は実装済みの組合せです。追加設計では因子と各値、成立しない組合せ、必須の拒否組合せを先に表にし、対象範囲を実装担当と合意します。権限境界は重要なので、ケース削減だけを目的にペアワイズへ置き換えません。画面寸法など別の因子は別表とし、採用した組合せと省略理由を記録します。
