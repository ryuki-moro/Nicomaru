# #121 成功ログイン時刻とリスク集計：統合・検証

基点は#104・#105・#120・#123統合済みの `b19f9bb`、作業ブランチは `codex/resume-last-login`。GitHub mainは `b426e99` と照合した。既存の未コミットmigrationと試験を取り込み、元チェックアウトは変更していない。

## 実装

`auth.users.last_sign_in_at` の変更をactiveな本人の `user_profiles.last_login_at` へ同期する。Auth認証後のプロフィール作成と招待有効化も扱い、既知の値を巻き戻さない。通常更新・任意日時の書込みでは活動時刻を進めず、同期関数はクライアントから直接実行できない。認証UIと認証APIは変更していない。

停止解除だけで停止中のAuth時刻を採用してしまう問題を追加試験で再現し、修正した。プロフィール更新からAuth値を読み直す経路を、初回作成・招待有効化・Authトリガーからの同期に限定した。停止解除後に未来日時を書き込んでも古いAuth値を活動へ取り込まず、新しい成功ログインまで既存値を保つ。既存データの補完は保護トリガーの作成前に行う。

リスク入力では、UTCの日付切り出しにより日本時間の深夜ログインが前日扱いになる問題を再現した。既存の `todayInJst` で活動日を求めるよう修正し、無反応判定が1日早まらないことを確認した。リスクのルール・閾値は変えていない。

## 検証

全単体・PGlite試験は1033件成功、実PostgreSQL用15件skip。型検査・lint・本番ビルドも成功した。

整形検査・進捗整合性検査も成功した。

関連試験はDB12件・集計入力4件・既存リスク判定32件の計48件が成功した。

- 本人だけの同期、時刻不変・古い値・NULL・通常更新での非更新、停止中・削除済み・招待中の除外。
- 招待有効化、認証後のプロフィール作成、任意日時の改ざん防止、停止前の値の保持、停止解除後の非更新。
- 認証トランザクションのrollback、Auth正本・同期関数への直接アクセス拒否、既存active行の補完。
- 両パートナーを対象にした最新ログインの取得、無反応理由の解除、活動なしの判定維持、新しい提出・フォローの優先、日本時間の日付境界。

DB試験はPGliteでAuth正本の変更をSQLから再現したもの。集計入力のSupabase応答は差し替えている。実GoTrueの認証呼出しと実PostgreSQLの並行接続の成功を示すものではない。

## 適用条件と未実施

追加migrationは `supabase/migrations/20261015000100_record_last_login.sql`。共有DBへの適用・実Auth試験・実利用データの再計算・main反映・push・PR作成は未実施。

1. 検証環境でmigration履歴を確認し、Authスキーマへのトリガー作成権限を持つ管理接続で適用する。この統合ブランチでは#121の `20261015000100` が#120の `20261023000100` より先に実行される。すでに後続migrationを適用した環境では、番号を変えたり適用履歴を補正したりせず、未適用分と適用順序を先に照合する。
2. OTP・パスワード・新メールリンク・旧PKCEリンク・初回登録・招待有効化で、activeな本人だけが更新されることを実Authで確認する。失敗・refresh・プロフィール編集・停止中の試行では進まないことも確認する。Authトリガーの失敗は認証トランザクションにも影響するため、共有反映前に確認する。
3. 既存補完は現在activeの行だけを対象とする。過去の状態履歴から停止中の認証だったかを復元するものではない。
4. 保存済みリスクsnapshotは自動では変わらない。既存の明示再計算または日次処理を実行した時点で反映される。画面更新だけを再計算の証拠にしない。

Authの日時項目は [公式User仕様](https://supabase.com/docs/guides/auth/users)、成功時の保存経路は [Auth v2.197.0のトークン発行実装](https://github.com/supabase/auth/blob/v2.197.0/internal/tokens/service.go) を参照した。これは共有環境の稼働版や実挙動の確認とは別に扱う。
