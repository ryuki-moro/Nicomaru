# 開発のはじめかた

GitHub を触ったことがない人向けの手順書です。専門用語はできるだけ使いません。
画面のボタンを押す順番どおりに書いてあるので、上から順にやれば進みます。

**この文書は2部構成です。**

- **準備** … 最初の1回だけやること（15〜20分）
- **毎回の作業** … Issue 1つにつき1周する6ステップ

---

## まず、たとえ話で

用語がまったく分からなくても、この6行だけ頭に入れば進めます。

| 用語 | たとえると |
| --- | --- |
| **リポジトリ** | みんなで使う**ファイル置き場**。にこまるのコード一式が入っている |
| **Issue** | **やることリストの1枚**。「#12」のように番号が付いている |
| **ブランチ** | 置き場をまるごと**コピーした自分専用の作業机**。ここで何をしても本体は壊れない |
| **コミット** | 作業の**セーブポイント**。「ここまでやった」と記録を残すこと |
| **プッシュ** | 自分のPCに溜めたセーブを**GitHubにアップロード**すること |
| **プルリクエスト** | 「自分の机の成果を本体に入れてください」という**お願い**。略してPR |

> 「ブランチを切る」という言い方をよくしますが、「切る」は**作る**という意味です。何も壊していません。

---

## 使う道具を選ぶ

黒い画面（コマンド）を使わずに操作できるアプリを使います。**どちらか好きなほうで構いません。**

| | GitHub Desktop | SourceTree |
| --- | --- | --- |
| 特徴 | シンプル。迷うところが少ない | 多機能。Issue へのジャンプを設定できる |
| おすすめ | **はじめての人** | 慣れている人・細かく操作したい人 |
| 入手先 | <https://desktop.github.com/> | <https://www.sourcetreeapp.com/> |

**この手順書では両方の操作を書きます。** 自分が使うほうだけ読んでください。

# 準備（最初の1回だけ）

## 1. リポジトリに入れることを確認する

**5人とも招待済みです。** <https://github.com/ryuki-moro/Nicomaru> を開いて、
中身が見えれば準備できています。

見えない場合は GitHub にログインしているか確認してください。
それでもだめならリーダーに連絡してください。

> 全員 **Write** 権限です。ブランチを作る・コミットする・
> Pull Request を出す・マージする、まで全部できます。

## 2. 道具を入れる

**GitHub Desktop の場合**
インストールしたら `Sign in to GitHub.com` を押して、GitHubアカウントでログインします。

**SourceTree の場合**
インストールしたら `ツール` → `オプション` → `認証` で GitHub アカウントを追加します。

## 3. ファイル置き場を自分のPCに持ってくる（クローン）

**GitHub Desktop の場合**
`File` → `Clone repository...` → 一覧から **ryuki-moro/Nicomaru** を選ぶ → `Clone`

**SourceTree の場合**
`新規...` → `URLからクローン` → URL に `https://github.com/ryuki-moro/Nicomaru.git` を入れる → `クローン`

保存先はどこでも構いませんが、**日本語やスペースを含まない場所**にしてください。

## 4. 準備の仕上げ

クローンしたフォルダで、ターミナルから1回だけ実行します。

```bash
npm install
```

これで必要な部品が入り、あわせて
**`main` に直接 push できないようにする安全装置**が有効になります。
うっかり `main` で作業してしまっても、push しようとした時点で止まります。

## 5.（SourceTree の人だけ）Issue へジャンプできるようにする

設定しておくと、**コミット履歴の中の `#12` がリンクになって、クリックでIssueに飛べます。**

1. `リポジトリ` → `リポジトリ設定` → `課題追跡`（Issue Tracking）
2. `追加` を押して、次のとおり入力する

| 項目 | 入れる値 |
| --- | --- |
| 課題追跡システム | `Basic URL` |
| 検索用の正規表現 | `#(\d+)` |
| リンク先URL | `https://github.com/ryuki-moro/Nicomaru/issues/$1` |

3. `OK` を押す

# 毎回の作業（この6ステップの繰り返し）

Issue 1つにつき1周します。慣れれば5分で回せます。

---

## ステップ1: Issue を選んで、自分を担当者にする

**場所: GitHub のWeb画面**

1. リポジトリの `Issues` タブを開く
2. やる予定のIssueを開く（例: **#12**）
3. 右側の **Assignees** の歯車を押して、**自分を選ぶ**
4. **左上の番号（#12）を覚える**。あとでブランチ名とコミットに使います

> **Assignees を必ず設定してください。**
> 誰も担当になっていないIssueは「まだ誰もやっていない」ように見えます。
> 2人が同じ作業を始めてしまう、いちばん多い事故がこれです。

Issueの中身は「やること」がチェックリストになっています。
**終わった項目はチェックを入れてください。** 他の4人が進捗を見るのはここです。

## ステップ2: 本体を最新にする

**場所: GUIツール**

**GitHub Desktop の場合**
上部の `Current Branch` が **`main`** であることを確認 → 右上の `Fetch origin` を押す
→ `Pull origin` に変わったら、もう一度押す

**SourceTree の場合**
左のブランチ一覧で `main` をダブルクリック → 上部の `プル` を押す

> **これを飛ばすと後で困ります。** 古い状態から作業を始めると、
> あとで衝突（コンフリクト）が起きやすくなります。

## ステップ3: 自分専用の作業机（ブランチ）を作る

**場所: GUIツール**

**GitHub Desktop の場合**
`Current Branch` を押す → `New Branch` → 名前を入れて `Create branch`

**SourceTree の場合**
上部の `ブランチ` アイコンを押す → 名前を入れて `ブランチを作成`

### 名前の付け方

**「種類 / issue-番号 - 内容」** の形にします。

```
feature/issue-19-e2e-core-flow     新しく作るもの
fix/issue-12-login-bug             不具合を直すもの
docs/issue-29-glossary             文書を書くもの
```

英語が思いつかなければローマ字で構いません。
**大事なのは番号を入れること**で、誰の何の作業か一目で分かるようにするためです。

<details>
<summary>ターミナルでやる場合</summary>

```bash
git switch main
git pull
git switch -c feature/issue-19-e2e-core-flow
```

</details>

## ステップ4: 直して、こまめにセーブ（コミット）する

**場所: GUIツール**

いつもどおりファイルを編集します。編集すると、変更したファイルが自動で一覧に並びます。

**GitHub Desktop の場合**
左下の `Summary` 欄にメッセージを書く → `Commit to ...` を押す

**SourceTree の場合**
変更したファイルにチェックを入れる → 下のメッセージ欄に書く → `コミット` を押す

### コミットメッセージに番号を入れる

```
ユーザーログイン時のエラーを修正 (#12)
```

**末尾に `(#12)` を付けてください。** こう書いておくと、
GitHub の Issue #12 のページに「このコミットがありました」と自動で表示されます。
あとから「この修正、どのIssueだっけ」を探さずに済みます。

> **GitHub Desktop の小ワザ**
> メッセージ欄で `#` を打つと、**Issueの一覧が出て選べます。**
> 番号を覚えていなくても大丈夫です。

### どのくらいの頻度でコミットする？

**キリのいいところで何度でも。** 1日ぶんを一度に入れるより、
小さく分けたほうが、あとで問題を見つけやすくなります。

メッセージは「提出画面のテストを追加 (#19)」のように、**やったことをそのまま**書けば十分です。

<details>
<summary>ターミナルでやる場合</summary>

```bash
git add -A
git commit -m "ユーザーログイン時のエラーを修正 (#12)"
```

</details>

## ステップ5: GitHubにアップロード（プッシュ）する

**場所: GUIツール**

**GitHub Desktop の場合**
右上の `Publish branch` を押す（2回目以降は `Push origin`）

**SourceTree の場合**
上部の `プッシュ` を押す → ブランチにチェックを入れて `プッシュ`

ここまでで、**自分の作業がGitHub上に保存されました。** PCが壊れても消えません。
まだ本体（`main`）には入っていないので、安心してください。

<details>
<summary>ターミナルでやる場合</summary>

```bash
git push -u origin feature/issue-19-e2e-core-flow
```

</details>

## ステップ6: 「本体に入れてください」とお願いする（Pull Request）

**場所: GitHub のWeb画面**

**GitHub Desktop の場合**
プッシュすると `Create Pull Request` ボタンが出ます。押すとブラウザが開きます。

**SourceTree の場合**
プッシュ後、GitHub のリポジトリを開くと上部に
`Compare & pull request` という緑のボタンが出ます。

### PR本文に必ずこの1行を入れる

```
Closes #12
```

**これを書いておくと、PRが本体に入った瞬間にIssue #12 が自動で閉じます。**
閉じ忘れが無くなります。

> `Closes` のほかに `Fixes` `Resolves` も使えます。どれでも同じです。
> **番号の前のシャープを忘れない**でください。`Closes 12` では効きません。

### そのあと

1. `Create pull request` を押す
2. 右側の `Reviewers` でチームの誰かを指定する
3. **緑のチェックが付くのを待つ**（GitHubが自動でテストを走らせています）
4. OKが出たら `Merge pull request` を押す
5. `Delete branch` を押して作業机を片付ける

次の作業は、また**ステップ1（Issueを選ぶ）から**始めてください。

# 絶対にやらないこと

これだけ守れば、取り返しのつかないことは起きません。

- **`main` で直接作業しない。**
  作業を始める前に、いま自分がどのブランチにいるか必ず見てください。

  もし忘れても、**push しようとした時点で自動的に止まります。**
  そのときは画面に出る案内どおりに直してください。

- **`.env.local` をコミットしない。**
  暗号化の鍵が入っています。GitHubに一度でも上がると、
  **鍵を作り直してデータを入れ替える羽目になります。**
  自動で除外される設定にはなっていますが、
  ファイル一覧に出てきたら手を止めて相談してください。

- **他の人のブランチを消したり、上書きしたりしない。** 自分が作ったブランチだけ触ります。

- **担当の範囲外のファイルを勝手に触らない。**
  必要になったら**先にチームに言ってから**にしてください。
  前回これができておらず、同じ処理が2か所に書かれて食い違う不具合が残りました（#18）。

# コードを書く人だけ、出す前に

設定作業や文書だけの担当は読み飛ばして構いません。

Pull Request を出す前に、この3つを実行して**全部通ることを確認**してください。
通らないまま出すと、CI（GitHubが自動で走らせる検査）が赤くなってレビューに進めません。

```bash
npm test        # テスト347件
npm run lint    # 書き方の検査
npm run typecheck
```

- **データベースの権限まわり（RLS）を触ったときは、必ず `npm test` を通す。**
  ここの不具合は目で見ても見つかりません。実際に動かして初めて出ます。
- **一覧・検索・集計の処理は `src/lib/services/` に置く。**
  画面とAPIの両方に同じものを書くと、片方だけ直して食い違います。
- **PRの画面で緑のチェックが付いてからレビューを頼む。** 赤いままだと相手の時間を無駄にします。

# 困ったとき

<details>
<summary><b>間違えて main で作業してしまった</b></summary>

**push しようとすると自動的に止まります。** こういう画面が出ます。

```
  ============================================================
   main には直接 push できません
  ============================================================
```

慌てなくて大丈夫です。**作業は消えていません。**

**まだコミットしていない場合**: ステップ3のとおりブランチを作ってください。
編集内容はそのまま新しいブランチに付いてきます。

**もうコミットしてしまった場合**: 次の3行で、コミットごと新しいブランチへ移せます。

```bash
git switch -c 作業内容のブランチ名
git switch main
git reset --keep origin/main
```

1行目で今のコミットを持ったまま新しいブランチを作り、
2〜3行目で `main` を GitHub 上の状態に戻しています。

自信がないときは自分で操作せず、**チームに声をかけてください。**

</details>

<details>
<summary><b>コンフリクトと出た</b></summary>

自分と他の人が**同じファイルの同じ行を直した**ときに出ます。故障ではありません。

ファイルを開くと `<<<<<<<` と `>>>>>>>` で挟まれた部分があります。
**どちらを残すか決めて、記号ごと消して**保存し、もう一度コミットします。

判断がつかないときは、**相手に直接聞いてから**にしてください。勝手に片方を消さないこと。

</details>

<details>
<summary><b>プッシュしようとしたら怒られた</b></summary>

だいたいは**他の人の変更が先に入っている**ためです。
プル（最新を取り込む）をしてから、もう一度プッシュしてください。

それでも出る場合はメッセージをそのままコピーしてチームに貼ってください。

</details>

<details>
<summary><b>CIが赤くなった（×が付いた）</b></summary>

PRの画面で **×印の横の `Details`** を押すと、何が失敗したか出ます。

だいたいは `npm test` か `npm run lint` の失敗です。
自分のPCで同じコマンドを実行すると、同じエラーが再現します。
直してからもう一度プッシュすれば、CIは自動でやり直します。

</details>

<details>
<summary><b>PRをマージしたのにIssueが閉じない</b></summary>

PR本文の書き方を確認してください。

- ✅ `Closes #12`
- ❌ `Closes 12`（シャープが無い）
- ❌ `close #12` と書いたつもりが、コミットメッセージのほうに書いていた

**PRの説明文（Description）**に書く必要があります。
間に合わなければ、Issueを手で閉じても構いません。

</details>

<details>
<summary><b>自分の作業が消えていないか不安</b></summary>

**プッシュ済みなら消えません。**
GitHubの `Branches` から自分のブランチ名を探せば、いつでも見られます。

不安なら**こまめにコミットしてプッシュする**のが一番の対策です。
1日の終わりに必ずプッシュする習慣にしてください。

</details>

<details>
<summary><b>何をすればいいか分からなくなった</b></summary>

自分がAssignees になっているIssueを開いて、
**チェックが付いていない一番上の項目**をやってください。それが今やるべきことです。

項目の意味が分からなければ、そのIssueにコメントで質問してください。
個人チャットではなくIssueに書くと、**他の人も同じ答えを見られます。**

</details>

## 1周の流れ（まとめ）

```
GitHub Web        Issueを開く → 自分をAssigneesに → 番号を覚える (#12)
     ↓
GUIツール         mainを最新に → ブランチを作る (fix/issue-12-login-bug)
     ↓
GUIツール         直す → コミット「…を修正 (#12)」→ プッシュ
     ↓
GitHub Web        PRを作る → 本文に「Closes #12」→ レビュー → マージ
     ↓
                  Issue #12 が自動で閉じる
```

全体の割当と、なぜその分担なのかは Issue **#23**（Epic）にまとめてあります。
