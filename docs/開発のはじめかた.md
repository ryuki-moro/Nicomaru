# 開発のはじめかた

GitHub を触ったことがない人向けの手順書です。専門用語はできるだけ使いません。
画面のボタンを押す順番どおりに書いてあるので、上から順にやれば進みます。

これまでは全員が同じ場所（`main`）に直接書き込んでいましたが、5人で同時に作業すると
**お互いの変更を上書きして壊してしまいます**。
そこでこれからは「自分専用の作業場所」を作ってから作業します。

---

## まず、たとえ話で

用語がまったく分からなくても、この5行だけ頭に入れば進めます。

| 用語 | たとえると |
| --- | --- |
| **リポジトリ** | みんなで使う**ファイル置き場**。にこまるのコード一式が入っている |
| **ブランチ** | 置き場をまるごと**コピーした自分専用の作業机**。ここで何をしても本体は壊れない |
| **コミット** | 作業の**セーブポイント**。「ここまでやった」と記録を残すこと |
| **プッシュ** | 自分のPCに溜めたセーブを**GitHubにアップロード**すること |
| **プルリクエスト** | 「自分の机の成果を本体に入れてください」という**お願い**。略してPR |

> 「ブランチを切る」という言い方をよくしますが、「切る」は**作る**という意味です。何も壊していません。

## 準備（最初の1回だけ）

1回やれば以降は不要です。15分くらい。

### 1. リポジトリに入れることを確認する

**5人とも招待済みです。** <https://github.com/ryuki-moro/Nicomaru> を開いて、
中身が見えれば準備できています。

見えない場合は GitHub にログインしているか確認してください。
それでもだめならリーダーに連絡してください。

> 全員 **Write** 権限です。ブランチを作る・コミットする・
> Pull Request を出す・マージする、まで全部できます。

### 2. GitHub Desktop を入れる

<https://desktop.github.com/> からダウンロードして入れます。
**黒い画面（コマンド）を使わずに操作できるアプリ**です。

起動したら `Sign in to GitHub.com` を押して、さっき作ったアカウントでログインします。

### 3. ファイル置き場を自分のPCに持ってくる

`File` → `Clone repository...` を押し、一覧から **ryuki-moro/Nicomaru** を選んで `Clone` を押します。

保存先はどこでも構いませんが、**日本語やスペースを含まない場所**にしてください。
`C:\dev\nicomaru` のような場所が安全です。

### 4. 準備の仕上げ

クローンしたフォルダで、ターミナルから1回だけ実行します。

```bash
npm install
```

これで必要な部品が入り、あわせて
**`main` に直接 push できないようにする安全装置**が有効になります。
うっかり `main` で作業してしまっても、push しようとした時点で止まります。

<details>
<summary>ターミナルでやる場合</summary>

```bash
git clone https://github.com/ryuki-moro/Nicomaru.git
```

</details>

## 毎回の作業（この6ステップの繰り返し）

1つのIssueにつき1周します。慣れれば5分で回せます。

### 1. 自分のIssueを開いて、番号を確認する

GitHubの `Issues` タブに、やることが一覧で並んでいます。
自分の担当を開き、**左上の番号（#19 など）を覚えます。** あとでブランチの名前に使います。

Issueの中身は「やること」がチェックリストになっています。
**終わった項目はチェックを入れてください。** 他の4人が進捗を見るのはここです。

### 2. 本体を最新にする

上部の `Current Branch` が **`main`** になっていることを確認し、右上の `Fetch origin` を押します。
`Pull origin` という表示に変わったら、もう一度押します。

> **これを飛ばすと後で困ります。** 古い状態から作業を始めると、あとで衝突（コンフリクト）が起きやすくなります。

### 3. 自分専用の作業机（ブランチ）を作る

`Current Branch` を押して `New Branch` を選び、名前を入れて `Create branch` を押します。

名前は **「Issue番号 - 内容を英語で短く」** の形にします。

```
19-e2e-core-flow
20-backup
21-verification-design
```

英語が思いつかなければローマ字で構いません。
**大事なのは頭に番号を付けること**で、誰の何の作業か一目で分かるようにするためです。

<details>
<summary>ターミナルでやる場合</summary>

```bash
git switch main
git pull
git switch -c 19-e2e-core-flow
```

</details>

### 4. 作業して、こまめにセーブ（コミット）する

いつもどおりファイルを編集します。編集すると GitHub Desktop の左側に
**変更したファイルが自動で並びます。**

左下の `Summary` 欄に**何をしたかを日本語で一行**書き、`Commit to ...` ボタンを押します。

> **キリのいいところで何度も**押してください。1日ぶんを一度に入れるより、
> 小さく分けたほうが、あとで問題を見つけやすくなります。
> メッセージは「提出画面のテストを追加」のように、**やったことをそのまま**書けば十分です。

<details>
<summary>ターミナルでやる場合</summary>

```bash
git add -A
git commit -m "提出画面のテストを追加"
```

</details>

### 5. GitHubにアップロード（プッシュ）する

右上の `Publish branch` を押します。2回目以降は `Push origin` という表示になります。

ここまでで、**自分の作業がGitHub上に保存されました。** PCが壊れても消えません。
まだ本体（`main`）には入っていないので、安心してください。

<details>
<summary>ターミナルでやる場合</summary>

```bash
git push -u origin 19-e2e-core-flow
```

</details>

### 6. 「本体に入れてください」とお願いする（プルリクエスト）

プッシュすると `Create Pull Request` というボタンが出ます。押すとブラウザが開きます。

本文に**この1行を必ず入れてください。**

```
Closes #19
```

こう書いておくと、**PRが本体に入った瞬間にIssueが自動で閉じます。** 閉じ忘れが無くなります。

あとは `Create pull request` を押し、右側の `Reviewers` でチームの誰かを指定します。
**OKが出たら `Merge pull request` を押して完了です。**

> マージが終わったら `Delete branch` を押して作業机を片付けます。
> 次の作業は、また**ステップ2（本体を最新にする）から**始めてください。

## 絶対にやらないこと

これだけ守れば、取り返しのつかないことは起きません。

- **`main` で直接作業しない。**
  作業を始める前に `Current Branch` を必ず見てください。
  `main` のままなら、ステップ3に戻ってブランチを作ります。

  もし忘れても、**push しようとした時点で自動的に止まります。**
  そのときは画面に出る案内どおりに直してください。

- **`.env.local` をコミットしない。**
  暗号化の鍵が入っています。GitHubに一度でも上がると、
  **鍵を作り直してデータを入れ替える羽目になります。**
  自動で除外される設定にはなっていますが、ファイル一覧に出てきたら手を止めて相談してください。

- **他の人のブランチを消したり、上書きしたりしない。** 自分が作ったブランチだけ触ります。

- **担当の範囲外のファイルを勝手に触らない。**
  必要になったら**先にチームに言ってから**にしてください。
  前回これができておらず、同じ処理が2か所に書かれて食い違う不具合が残りました（#18）。

## コードを書く人だけ、出す前に

設定作業や文書だけの担当（#14・#21）は読み飛ばして構いません。

プルリクエストを出す前に、この3つを実行して**全部通ることを確認**してください。
通らないまま出すと、CI（GitHubが自動で走らせる検査）が赤くなってレビューに進めません。

```bash
npm test        # テスト347件
npm run lint    # 書き方の検査
npm run typecheck
```

- **データベースの権限まわり（RLS）を触ったときは、必ず `npm test` を通す。**
  ここの不具合は目で見ても見つかりません。実際に動かして初めて出ます。
- **一覧・検索・集計の処理は `src/lib/services/` に置く。**
  画面とAPIの両方に同じものを書くと、片方だけ直して食い違います。
- **PRの画面で緑のチェックが付いてからレビューを頼む。** 赤いままだと相手の時間を無駄にします。

## 困ったとき

<details>
<summary><b>間違えて main で作業してしまった</b></summary>

**push しようとすると自動的に止まります。** こういう画面が出ます。

```
  ============================================================
   main には直接 push できません
  ============================================================
```

慌てなくて大丈夫です。**作業は消えていません。**

**まだコミットしていない場合**: ステップ3のとおりブランチを作ってください。
編集内容はそのまま新しいブランチに付いてきます。

**もうコミットしてしまった場合**: 次の3行で、コミットごと新しいブランチへ移せます。

```bash
git switch -c 作業内容のブランチ名
git switch main
git reset --keep origin/main
```

1行目で今のコミットを持ったまま新しいブランチを作り、
2〜3行目で `main` を GitHub 上の状態に戻しています。

自信がないときは自分で操作せず、**チームに声をかけてください。**

</details>

<details>
<summary><b>コンフリクトと出た</b></summary>

自分と他の人が**同じファイルの同じ行を直した**ときに出ます。故障ではありません。

ファイルを開くと `<<<<<<<` と `>>>>>>>` で挟まれた部分があります。
**どちらを残すか決めて、記号ごと消して**保存し、もう一度コミットします。

判断がつかないときは、**相手に直接聞いてから**にしてください。勝手に片方を消さないこと。

</details>

<details>
<summary><b>プッシュしようとしたら怒られた</b></summary>

だいたいは**他の人の変更が先に入っている**ためです。
`Fetch origin` → `Pull origin` を押してから、もう一度プッシュしてください。

それでも出る場合はメッセージをそのままコピーしてチームに貼ってください。

</details>

<details>
<summary><b>CIが赤くなった（×が付いた）</b></summary>

PRの画面で **×印の横の `Details`** を押すと、何が失敗したか出ます。

だいたいは `npm test` か `npm run lint` の失敗です。
自分のPCで同じコマンドを実行すると、同じエラーが再現します。
直してからもう一度プッシュすれば、CIは自動でやり直します。

</details>

<details>
<summary><b>自分の作業が消えていないか不安</b></summary>

**プッシュ済みなら消えません。**
GitHubの `Branches` から自分のブランチ名を探せば、いつでも見られます。

不安なら**こまめにコミットしてプッシュする**のが一番の対策です。
1日の終わりに必ずプッシュする習慣にしてください。

</details>

<details>
<summary><b>何をすればいいか分からなくなった</b></summary>

自分のIssueを開いて、**チェックが付いていない一番上の項目**をやってください。それが今やるべきことです。

項目の意味が分からなければ、そのIssueにコメントで質問してください。
個人チャットではなくIssueに書くと、**他の人も同じ答えを見られます。**

</details>
