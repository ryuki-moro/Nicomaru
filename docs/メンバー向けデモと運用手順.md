# メンバー向けデモと運用手順

対象は学校の制作・最終発表です。Agent AIの契約は不要です。ソース修正は担当者がPRで提出し、ほかのメンバーはブラウザーと記入用資料で試験・評価・発表準備を進められます。

## 最初に開くもの

1. [環境の使い分け](環境の使い分け.md)でローカルSupabaseを用意する。Dockerが使えないPCは環境担当の画面共有で操作確認し、利用可能な接続先を環境担当に確認する。
2. `npm ci`、`npm run demo:seed`、`npm run dev` を実行する。模擬データの作成先とログイン情報はローカルだけで扱う。
3. アプリを `http://127.0.0.1:3000` で開く。別名の `localhost` と混在させない。
4. 実施版を `git rev-parse HEAD` で確認し、試験仕様書の版欄へ記入する。

共有クラウドのDBを初期化する必要はありません。`supabase db reset` はローカル専用として扱います。
ブラウザーのプロファイル、シークレットウィンドウなどでプランナーと新郎新婦のセッションを分けます。

## 10分のデモ進行

| 目安   | 役             | 操作                                                   | 確認する結果                                     |
| ------ | -------------- | ------------------------------------------------------ | ------------------------------------------------ |
| 0–2分  | planner        | ダッシュボードから期限超過の模擬案件を開く             | リスクと根拠、未提出宿題が分かる                 |
| 2–4分  | planner/couple | 未登録のdemo-05の招待URLを別ブラウザーで開き、初回登録 | 同じ案件に紐付き、次にやることが見える           |
| 4–6分  | couple         | 「BGMリクエスト」など文字形式の宿題を保存・提出        | 下書きと提出済みを区別できる                     |
| 6–8分  | planner/couple | 提出物を不備ありにし、修正再提出後に確認済みにする     | 差し戻し理由と状態が双方で一致する               |
| 8–9分  | planner        | 準備シートを開き、AI停止時の案内と手動入力を見せる     | AIを起動しなくても作業を続けられる               |
| 9–10分 | system_admin   | `/system` を開く                                       | 容量の取得日時、上限未設定、監視通知を区別できる |

模擬メールはローカルMailpit `http://127.0.0.1:54324` で確認します。6桁コードとログインリンクは他人に転送せず、その場で使います。
外部メール・LINEの実送信はこのデモの必須条件にしません。LINE連携は自動試験の署名検証・送信SDKの模擬結果を説明し、実機との接続済みとは説明しません。

## 役割ごとの試験

| 役割         | 担当できる確認                                       | 期待される権限                                   |
| ------------ | ---------------------------------------------------- | ------------------------------------------------ |
| couple       | 招待、コード入力、下書き、提出、再提出、履歴、小画面 | 自分たちの案件。管理画面は操作できない           |
| planner      | 案件、宿題、提出確認、フォロー、準備シート           | 担当範囲の案件。式場・システム設定は管理者の範囲 |
| admin        | 式場内の利用者・テンプレートなど                     | 所属式場内。別式場の情報は参照できない           |
| system_admin | 式場、監視、容量、ログ                               | システム管理。一般メンバーにこの権限を配らない   |

試験に失敗したら「操作前の状態・操作・期待結果・実際の結果・対象版・ブラウザー」をIssueへ記録します。パスワード、メール本文、招待URL、Cookie、署名付きファイルURLは画像やログに入れません。

## AIデモを担当する人の手順

アプリのローカルLLMと開発用Agent AIは別です。ほかのメンバーにCodexの契約は不要です。
既存実装の既定モデルは`gemma3:12b`、設定例は`qwen2.5:7b`です。機器のVRAM・モデルの利用条件と学校の持込条件を確認した担当者が選びます。この資料はそのPCで推論済みという実績ではありません。

1. 模擬データの接続先・アプリ版を確認する。
2. `AI_WORKER_DATABASE_URL` は専用`ai_worker`ロールの接続情報を設定する。Supabase Service Role KeyをワーカーPCへ配布しない。DBの権限はmigrationと`tests/db/ai.test.ts`などで確認する。
3. Ollamaを担当PC内で起動し、`OLLAMA_ENDPOINT`をその接続先、`OLLAMA_MODEL`を導入済みモデルへ設定する。外部公開は不要。
4. 必要な環境変数を設定したターミナルで `npm run worker:ai` を実行する。起動元とプロセスを記録する。
5. アプリの準備シート等から匿名の入力で依頼する。結果は人が読み、採用する内容だけ業務欄へ反映する。未検証の生成内容をそのまま送信しない。
6. 終了は起動したワーカーのターミナルで`Ctrl+C`。心拍が10分を超えて古くなると依頼ボタンが消える。すでに投入したジョブの状態は別に確認する。
7. 停止中は案件・提出・確認・手動入力を続ける。復帰時はワーカーを再起動し、新しい心拍とジョブの状態を確認する。

推論を使わない事前確認は `npm test` とCIの `ai-availability.spec.ts` で行えます。実モデルの品質評価は評価票に人が記入し、自動試験の合格率と混ぜません。

## 環境担当の確認表

`node --env-file=.env.local --import tsx scripts/check-environment.mts` は値を表示せず設定の形式と有無を調べます。DBや外部サービスへ変更は加えません。

| 確認                 | 判断                                                                                                   |
| -------------------- | ------------------------------------------------------------------------------------------------------ |
| アプリとAuthの戻り先 | `APP_BASE_URL`とSupabaseのSite URL/許可Redirect URLを同じscheme・host・portにする                      |
| 認証メール           | ローカルはMailpitを使い、メールテンプレートに6桁Tokenがあることを確認                                  |
| DBとStorage          | 同じSupabaseプロジェクト。追加migrationを適用してから新しいアプリを起動                                |
| 容量                 | `DB_CAPACITY_LIMIT_BYTES`と`STORAGE_CAPACITY_LIMIT_BYTES`は契約の実値。空欄はS03で「未設定」           |
| 定期処理             | 公開先が決まった場合のみDB管理者が`register_scheduled_jobs`で登録。localhostはクラウドcronから到達不可 |
| 内部認証             | アプリと登録側の`INTERNAL_CRON_SECRET`を一致させる。値をIssueへ残さない                                |
| モニター             | `MONITOR_ENABLED_JOBS`に実際に動かすジョブだけ指定。S03通知とActionsの失敗を両方確認                   |
| 公開範囲             | ローカルデモか学校内共有かを明記。学外公開や新規有料契約を前提にしない                                 |

LINE内ブラウザーは通常URL・OTP導線を実機で確認してから判断します。現時点ではLIFF専用実装を追加する根拠がないため、採用を保留します。端末試験票に環境と制約を記入します。

## 秘密情報の管理と担当交代

- 管理責任者は学校チームで1名決め、名前は非公開の管理台帳へ記入する。共有資料には鍵の値を置かない。
- `.env.local`・`.env.demo`・ワーカー環境は各担当PCで保管し、Gitに追加しない。必要な役割の人に、チームで合意した秘密情報共有手段で渡す。
- 鍵の管理台帳には「環境・キー名・責任者・更新日・影響先・旧鍵失効確認日」だけを記録する。
- 送信APIキー・内部cron secret・ワーカー接続パスワードを更新するときは、新しい値を必要な接続先へ設定→接続確認→旧値を失効、の順にする。
- `PII_ENCRYPTION_KEY`は暗号化済みデータに対応するため、単純に上書きしない。移行プログラムと復号確認を別途用意する。`PII_HMAC_KEY`の更新も検索・トークン照合への影響を確認する。
- 離脱者のGitHub/Supabase/公開先の権限を外し、その人が知っている共有秘密値を更新する。残る担当者の接続確認と旧資格情報の失効を記録する。

実端末試験、メンバーの試用、機器/モデルの選定、正式な発表日と分担は本人が確認します。記入欄の空白は未実施であり、合格扱いにはしません。
