# 実装計画: 式場の詳細・編集と動作確認の区切り

## 目的とスコープ

- 2026-10-08の「実装を進め、動作確認できる段階で止める」に基づき、GAP-01 / F-8-3 / Issue #54の式場編集を最初の確認単位とする。
- Done: system_adminが一覧から式場を開き、名称・代表メール・利用状態を保存できる。再読込と一覧に保存内容が反映され、認可・入力・通信失敗を検証できる。
- 式場コードは既存仕様どおり変更不可。管理者アカウント操作は既存の利用者管理を使う。
- 全更新APIへのOrigin検証、削除バッチ、容量集計等の別機能は、今回の動作確認後の作業とする。

## 前提と制約

- Next.js / React / Supabase / Zod、既存のUI・エラー・RLS規約を使う。新規ライブラリ・DB migrationは不要。
- 現在の改善/資料ブランチを基点に作業ブランチを作る。mainへのマージはこの区切りに含めない。
- 模擬データで検証する。アプリの本番運用は予定なし。ローカルNext.jsから既存の検証用Supabaseに接続する場合は、その構成を明記する。
- venues.activeは利用状態のフラグであり、所属利用者を一括ログアウトする機能として説明しない。

## 現状把握

- `src/app/(staff)/venues/page.tsx` と `VenueForm.tsx` は未実装の `/venues/{id}` へリンクしている。
- `src/lib/validation.ts` のvenueUpdateSchemaは名称・代表メール・利用中の3項目を定義済み。
- `src/lib/auth/session.ts`、`src/lib/api/route.ts`、`src/lib/api/client.ts` と利用者編集画面のUIを再利用する。
- DBのvenues_writeはsystem_admin限定。更新日時のトリガーとactorをauth.uid()から取得するlog_auditが存在する。

## 設計方針

| 判断 | 採用 | 理由 |
| --- | --- | --- |
| 詳細取得 | Server ComponentからRLS付きselect | 既存規約どおり。専用GET APIを増やさない |
| 更新 | `/api/venues/[venueId]` のPATCH | 明示的な許可項目だけを更新し、フォームから共通api.patchで呼べる |
| 認可 | system_adminの検証＋RLS | Service Roleで業務更新を行わない |
| 入力 | 未知キー・空の更新を拒否 | コードや管理者情報を送っても成功扱いにしない |
| リクエスト元 | 新PATCHのみ同一Origin必須 | ブラウザの更新元を確認し、他APIへの展開はGAP-06で管理 |
| 監査 | 既存log_auditへ変更項目名を記録 | 氏名・メールの値を重複保存せず、実行者はDB側で解決 |

## 実装ステップ

1. API・入力・権限: スキーマ、新PATCH、Origin検証、単体/RLSテスト。正常更新・null消去・未指定維持・401/403/404/400・DB失敗を確認する。
2. 画面・導線: 詳細ページ、編集フォーム、system画面から一覧へのリンク。保存中/成功/項目エラー/取得失敗を表示する。APIの応答契約確定後、実装はStep 1と並行可能。
3. 通し検証と受け渡し: 専用fixtureでPC/スマートフォンの保存・再読込・一覧・権限外・不正入力を試す。lint/型/テスト/ビルドを確認し、ユーザー用の模擬式場と確認手順を用意して停止する。

## リスクと未確定事項

- 既存の検証DBを使う場合も、専用fixtureだけを作成・変更・清掃する。既存の式場・利用者は変更しない。
- 更新対象なしとDB通信失敗を区別する。監査失敗は既存APIと同じくログ記録し、成功済み更新を二重実行させない。
- 式場の停止と利用者アカウント停止を混同しない。

## 検証計画

- API/入力/Originの単体テストと実SQLのRLS検証。
- ブラウザで一覧→詳細→変更→再読込→一覧反映。任意メール消去、不正入力、コード変更不可、認可拒否、通信失敗からの再試行。
- 専用模擬式場をユーザーの動作確認用に残し、URLとローカル専用のログイン案内を渡す。ここで次機能への実装を止める。
