# 削除バッチの失敗処理と依存更新

## 目的とスコープ

GAP-11の削除失敗を成功として数える問題と、Issue #47の依存監査失敗を解消する。
既存の180日保持期間、削除・匿名化対象、内部cron認証を維持する。
本番運用・実データの削除・AI推論・メールやLINEの送信は今回の検証対象外。

## 前提と制約

- 学校デモ向けの開発。実装依頼に基づき、PR #68を土台として変更する。
- DBマイグレーションは追加しない。実体削除とDB操作を一つのトランザクションにはできない。
- 削除は戻せないため、エラー注入は模擬クライアントで行う。実案件に削除APIを実行しない。
- 監査ログ・通知送信ログを残す既存方針を維持する。自由記述や利用者への参照を含む、全PIIの完全消去を保証する変更ではない。

## 現状把握と設計方針

Storageの削除結果と複数のDB操作結果を確認せず成功件数に加算していた。
実体削除に失敗した場合もメタデータが消え、再実行でファイルを辿れなくなる。
対象案件の200件制限には完了マーカーがなく、201件目以降が取り残され得る。
ファイル・宿題一覧も取得上限を考慮していなかった。

各操作の結果を確認し、実体削除が成功したファイルのメタだけ削除する。
失敗した案件の以降の処理を止め、他案件と独立したAI保持期間処理は続ける。
すべての工程が完了した案件だけ成功件数に数える。一部失敗はHTTP 500とし、
成功件数・失敗件数・失敗工程を`batch_runs`へ記録する。上流のエラー本文は保存しない。
失敗例の記録は20件を上限とし、総失敗件数は省略しない。

案件・ファイル・宿題をID順のkeysetで取得し、200件をページサイズとして全件走査する。
完了マーカー方式は復元・再アーカイブ・更新権限の設計を伴うため採用しない。
過去の成功案件も日次で冪等に再処理するコストは残る。大量データの運用に移行する場合は、
処理時間と再開位置を別途設計する。

共通`runBatch`は開始記録が保存できなければ処理を開始せず、終了記録の失敗も検出する。
処理失敗と記録失敗が重なった場合は元の失敗を維持し、安全な補助ログを残す。

## 実装ステップ

1. `src/lib/api/internal.ts`、削除API、`src/lib/batches/case-purge.ts`を修正。
   失敗時の情報保持・部分成功・全ページ到達・180日境界・実行記録失敗を単体試験で確認する。
2. 独立して`package.json`/lockfileのNext.js・eslint-config-nextを15.5.27、sharpを0.35.5へ更新。
   既存lint互換層を維持し、監査0件とlint負例の検出を確認する。
3. 全体lint・型検査・単体/SQL/RLS・本番ビルド・PC/スマートフォン寸法のChromeで既存導線を検証する。
   CIで実PostgreSQL・実WebKit・秘密情報検査も確認し、結果をIssueと進捗台帳へ記録する。

## リスクと検証計画

- 部分削除後の再実行: Storage実体だけ削除済みでもメタを保持し、再実行で完了できることを試験する。
- 通信例外とDBエラー: 工程名だけを記録し、個人情報や秘密を含む上流本文が出ないことを試験する。
- 一覧取得失敗とAI整理失敗: 案件の成功・失敗件数と独立したフラグで記録する。
- 依存更新: Next.js 15系のパッチ更新に限定し、監査閾値やセキュリティ検査は変更しない。
- 実行中の案件復元との競合やスケジューラーの多重実行制御は既存設計に依存する。
