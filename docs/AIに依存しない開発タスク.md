## 1. APIがHTML・不正JSONを返しても、ログイン・権限エラーの画面遷移を維持する

[Issue #42](https://github.com/ryuki-moro/Nicomaru/issues/42)

### これは何をするIssue？

APIがHTMLや壊れたJSONを返した場合も、利用者が正しいエラー案内を受けられるようにします。AIサーバー・LLM・外部サービスの設定なしで実装できます。

### 現状と再現方法

main `cc575f9` の `src/lib/api/client.ts` はHTTPステータスを確認する前に `JSON.parse(text)` を実行します。fetchをモックして403でHTML、404でJSONの `null` を返すと、SyntaxError/TypeErrorになり、既存の `handleApiError` が `/error?code=403/404` へ遷移しません。401でも同じ問題があります。

### やること

- [ ] 非JSON・空・null・形式の違うエラー本文を安全な共通エラーに変換する
- [ ] 元のHTTPステータスを維持し、401はログイン、403/404は既存エラーページへ遷移する
- [ ] 正常なJSONエラーのmessage・details、成功JSON、204の既存挙動を維持する
- [ ] fetchモックでHTML、不正JSON、null、不正details、ネットワーク不通の回帰テストを追加する

### 終わったと言える条件

不正な本文でもエラー処理自体が例外にならず、401/403/404の遷移と400/422の項目エラー表示がテストで確認できること。lint・型チェック・テスト・ビルドが通ること。

### 優先度・難易度

- **優先度**: High
- **難易度**: ★★☆ ふつう

### 備考

対象: `src/lib/api/client.ts` と `tests/unit/api-client.test.ts`。#18の共通エラー処理導入は実装済みであり、このIssueはHTTP応答の解析失敗でその処理を通れなくなる不具合を扱います。

## 2. 一覧画面のページ番号を共通検証し、小数・無限大・巨大値による取得エラーを防ぐ

[Issue #43](https://github.com/ryuki-moro/Nicomaru/issues/43)

### これは何をするIssue？

案件・利用者・通知・宿題などの一覧に指定するページ番号を安全に解釈します。AIや外部連携なしで実装・検証できます。

### 現状と再現方法

main `cc575f9` では `Math.max(Number(params.page) || 1, 1)`、`parseInt`、各画面に重複した `resolvePage` の3方式があります。`/cases?page=1.5` や `/notifications?page=Infinity` は小数・無限大をoffsetへ渡します。他の一覧でも巨大な整数が通り、DBの範囲を超えます。

### やること

- [ ] 共通のページ番号解析関数を用意し、正の10進整数だけ受け入れる
- [ ] DBのoffset上限を超える値・配列・小数・負数・文字列・無限大を1ページ目に寄せる
- [ ] staff/coupleの全一覧画面と `GET /api/admin/users` に適用する
- [ ] 検索条件・タブ・並び順・50件単位を維持する
- [ ] 正常値、異常値、上限前後のユニットテストを追加する

### 終わったと言える条件

ページ番号の解析が1か所になり、全呼び出し元から有限で安全な整数だけDBへ渡ること。既存のページ送り・検索条件が維持され、lint・型・テスト・ビルドが通ること。

### 優先度・難易度

- **優先度**: Medium
- **難易度**: ★★☆ ふつう

### 備考

対象: `src/lib/pagination.ts`、`tests/unit/pagination.test.ts`、各一覧page.tsx、users API。DB構造やRLS変更は不要。

## 3. 通知ログCSVの期間を画面で指定し、終了日の全件を日本時間で出力する

[Issue #44](https://github.com/ryuki-moro/Nicomaru/issues/44)

### これは何をするIssue？

システム管理者が通知ログCSVの開始日・終了日を指定できるようにします。AI機能を使わずに開発できます。

### 現状と再現方法

main `cc575f9` の `src/app/(staff)/system/page.tsx` は期間なしのCSVリンクだけです。APIはfrom/toを検証せず `gte/lte('created_at', value)` へ渡します。`to=2026-10-06` では同日の深夜より後の記録が含まれず、画面の日本時間表示とも一致しません。

### やること

- [ ] システム画面に開始日・終了日の入力とCSV出力操作を追加する
- [ ] YYYY-MM-DDの実在日・開始日≦終了日を検証し、不正入力は共通の400形式で返す
- [ ] 開始日のJST 00:00以上、終了日の翌日JST 00:00未満で取得する
- [ ] 未指定・片側指定・同日・月末・うるう日・不正日・逆転期間をテストする
- [ ] 既存のsystem_admin権限、個人情報を含めない列、BOM・数式対策を維持する

### 終わったと言える条件

画面で期間を指定でき、終了日23:59台の記録を含み、翌日の記録を含まないこと。未認証・権限不足・不正期間も検証できること。

### 優先度・難易度

- **優先度**: Medium
- **難易度**: ★★☆ ふつう

### 備考

対象: `src/app/api/system/notification-logs.csv/route.ts`、`src/app/(staff)/system/page.tsx`、期間検証とテスト。CSVの取得件数上限は別Issueとして扱います。

## 4. 通知ログCSVがSupabaseの1,000件上限で欠落しないように分割取得する

[Issue #45](https://github.com/ryuki-moro/Nicomaru/issues/45)

### これは何をするIssue？

通知ログが1,000件を超えても、設計の最大10,000件までCSVに含めます。AI機能の実行は不要です。

### 現状と再現方法

main `cc575f9` のCSV APIは `limit(CSV_MAX_ROWS + 1)` で10,001件を一度に要求していますが、`supabase/config.toml` のAPI設定は `max_rows = 1000` です。1,001件以上のログがあると取得結果が1,000件で切れ、`buildCsv` は上限以内と判断して `x-truncated: false` を返します。成功したように見えて記録が欠落します。

### やること

- [ ] APIの1回あたり上限以内で、通知ログを複数ページに分けて取得する
- [ ] created_atに加えてidなどの一意なキーで安定した順序を保証する
- [ ] 最大10,001件を読み、CSVは10,000件、超過時は `x-truncated: true` とする
- [ ] 途中ページの失敗は失敗として扱い、不完全なCSVを成功で返さない
- [ ] 0/1,000/1,001/10,000/10,001件、同時刻ログ、取得失敗をテストする
- [ ] 管理画面で超過時に期間を絞る案内を表示する

### 終わったと言える条件

Supabaseのmax_rows=1000のままで1,001件が欠落なく出力されること。10,000件上限と超過表示を実際のレスポンスで確認できること。RLS・権限・個人情報を含めない列を維持すること。

### 優先度・難易度

- **優先度**: High
- **難易度**: ★★☆ ふつう

### 備考

対象: CSV API・分割取得処理・管理画面と関連テスト。期間指定の改善と組み合わせて確認します。API全体のmax_rowsを引き上げる変更は不要です。
