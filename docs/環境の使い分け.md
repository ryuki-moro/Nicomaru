# 環境の使い分け（デモ・テスト）

Issue #24。「どこで・何のために・どの接続先で動かすか」と、
模擬データでデモや試験を毎回同じ状態に戻す手順をまとめたページです。

> **前提（2026-10-08 の見直し）**
> 2月の「本番」は**学校の最終発表・デモ**のことです。アプリの本番運用（実際の新郎新婦のデータを預かる・常時稼働・商用化）は予定していません。
> そのため、**本番環境・ステージング環境は新しく作りません**。
> デモも検証も、**架空の模擬データだけ**で行います。

---

## 1. 環境は3つだけ

| | ① ローカル | ② CI（GitHub Actions） | ③ 共有デモ環境 |
| --- | --- | --- | --- |
| **何のため** | 開発・手での動作確認・発表リハーサル・スクリーンショット | Pull Request ごとの自動テスト | 先生・他の人が**自分の端末から**触るとき（必要な場合だけ。→[4章](#4-共有デモ環境は要るか)） |
| **どこで動く** | 各自のPC | GitHub のサーバー（毎回使い捨て） | Supabase のクラウド（無料プラン）＋アプリの公開先 |
| **データベース** | ローカル Supabase（Docker） | PGlite／Postgres 17／ローカル Supabase（CI 内） | Supabase プロジェクト 1つ |
| **入っているデータ** | `seed.sql` ＋ 模擬データ（`npm run demo:seed`） | テストごとに作って捨てる | `seed.sql` ＋ 模擬データ（`--remote`） |
| **接続先の設定** | `.env.local` | `.github/workflows/ci.yml` の中で自動生成 | `.env.demo`（各自のPC、コミットしない）とアプリの公開先の環境変数 |
| **鍵の扱い** | `npx supabase status` の固定値（外部から使えない）。PII の鍵は各自で生成 | 実行のたびに乱数で生成。保存しない | **リポジトリに書かない**。チームの連絡手段で、環境担当から必要な人にだけ渡す |
| **メール** | ローカルの受信箱 Mailpit（<http://127.0.0.1:54324>）に届く。外には出ない | Mailpit（CI 内） | 送らない前提（→ 3-3） |
| **誰が準備する** | 各自 | 自動（設定済み） | 環境担当 |

**「ステージング」「本番」という名前の環境はありません。** 資料や会話で「本番」と言うときは、2月の発表会のことです。

### 接続先の早見表

ローカルの値は `supabase/config.toml` で決まっています（全員同じ）。

| 用途 | ① ローカル | ③ 共有デモ環境 |
| --- | --- | --- |
| アプリ | `http://127.0.0.1:3000` | 環境担当が下の表に記入 |
| Supabase API | `http://127.0.0.1:54321` | `https://<project-ref>.supabase.co` |
| データベース（模擬データ投入用） | `postgres://postgres:postgres@127.0.0.1:54322/postgres` | Supabase の Connect → 接続文字列 |
| 管理画面（Studio） | `http://127.0.0.1:54323` | Supabase ダッシュボード |
| 受信箱（Mailpit） | `http://127.0.0.1:54324` | なし |

> `localhost` ではなく **`127.0.0.1`** を使ってください。ログイン後の戻り先（`auth.site_url`）が `127.0.0.1` なので、
> `localhost` で開くとメール認証のあとにログインできないことがあります。

## 2. 模擬データ

### 2-1. 中身

`scripts/demo/scenario.ts` に定義した**架空の**プランナー1人・案件5件です。
実在の人の名前・メールアドレス・写真は使いません。メールアドレスは予約ドメイン `.test` なので、間違って送っても外部には届きません。

挙式日は「**実行した日から何日後**」で決めています。発表の前日に作り直しても、画面に出る状況はいつも同じになります。

| 案件 | 挙式 | 見せたいこと |
| --- | --- | --- |
| demo-01 青木様 | 約3週間後 | 重要な宿題が期限切れ → リスク「高」 |
| demo-02 石井様 | 約2か月後 | 不備ありで差し戻した宿題・確認待ち・確認済みが1件ずつ |
| demo-03 上田様 | 約1か月半後 | 確認待ちの提出が2件（ゲストリストも期限切れ） |
| demo-04 岡田様 | 約4か月後 | 順調な案件（比較用） |
| demo-05 小川様 | 約5か月後 | 新郎新婦がまだ招待URLを開いていない → **その場で初回登録を実演できる** |

プランナー: `planner@nicomaru.test`（佐藤 花子）

### 2-2. 入れ方（ローカル）

前提: Docker Desktop が動いていること。

```bash
npx supabase start          # 初回は数分。終わると鍵が表示される
npx supabase db reset       # まっさらにして migrations と seed.sql を流す（任意）
npm run demo:seed           # 模擬データを入れる
npm run dev                 # http://127.0.0.1:3000
```

`.env.local` に必要なのは `NEXT_PUBLIC_SUPABASE_URL`・`NEXT_PUBLIC_SUPABASE_ANON_KEY`・`SUPABASE_SERVICE_ROLE_KEY`・
`PII_ENCRYPTION_KEY`・`PII_HMAC_KEY`・`APP_BASE_URL=http://127.0.0.1:3000`（書き方は [tests/e2e/README.md](../tests/e2e/README.md)）。

終わると、プランナーのログイン情報・作った案件・**未登録の新郎新婦の招待URL**が表示されます。

| やりたいこと | コマンド |
| --- | --- |
| 模擬データを入れる（既にあれば何もしない） | `npm run demo:seed` |
| 消して入れ直す（日付を今日基準に揃える） | `npm run demo:reset` |
| 新郎新婦のログイン用リンクも出す | `npm run demo:seed -- --login-links` |
| リスク表示まで揃える | `.env.local` に `INTERNAL_CRON_SECRET` を入れ、アプリを起動した状態で実行する |

- **新郎新婦としてログインする**: ログイン画面でメールアドレス（例 `demo-02-groom@demo.nicomaru.test`）を入れ、Mailpit に届いた6桁のコードを入れる。
  または `--login-links` で出たリンクを開く（1回きり・1時間で失効）。
- **消えるもの**: `demo:reset` が消すのは模擬データの案件（備考が `[demo:` で始まるもの）だけです。自分で作った案件やアカウントは消えません。
- **途中で失敗したとき**: データベース側は丸ごと元に戻ります（中途半端な案件は残りません）。

### 2-3. 入れ方（共有デモ環境）

環境担当だけが行います。接続先を `.env.demo` に書きます（`.env.*` は Git に入りません）。

```bash
# .env.demo の例（値は環境担当から受け取る）
NEXT_PUBLIC_SUPABASE_URL=https://<project-ref>.supabase.co
SUPABASE_SERVICE_ROLE_KEY=<service role key>
# Supabase の Connect →「Session pooler」（ポート 5432）の値。Transaction pooler（6543）は使えない
DEMO_DATABASE_URL=postgres://postgres.<project-ref>:<db password>@<host>:5432/postgres
PII_ENCRYPTION_KEY=<アプリの公開先と同じ値>
PII_HMAC_KEY=<アプリの公開先と同じ値>
APP_BASE_URL=https://<アプリの公開URL>
DEMO_PLANNER_PASSWORD=<12文字以上。チーム内でだけ共有>
```

```bash
npx tsx --env-file=.env.demo scripts/seed-demo.mts --remote --login-links
```

安全装置:

- 接続先がローカル以外のときは、`--remote` を付けないと動きません。
- `--remote` のときは、Supabase とデータベースの**両方**が共有デモ環境を向いていないと止まります（片方だけローカル、を防ぐ）。
- 共有デモ環境ではプランナーのパスワードを `DEMO_PLANNER_PASSWORD` で必ず指定します（固定値は使わない）。
- `PII_ENCRYPTION_KEY`／`PII_HMAC_KEY` はアプリ側と**同じ値**にしてください。違うと画面で氏名が読めません。

### 2-4. 守ること

- **実在の人の情報を入れない。** 家族・友人の名前、本物のメールアドレス、本物の写真も使わない。
- 画面で新しく案件を作るときも、名前は架空、メールは `@○○.test` にする。
- スクリーンショット・発表スライドは模擬データの画面から撮る。
- 共有デモ環境の鍵・パスワードを、リポジトリ・Issue・スライドに書かない。

## 3. 共有デモ環境のつくり方（環境担当）

**作ると決めた場合だけ**行います（→ 4章）。どれも管理画面での手作業です。

### 3-1. Supabase

- [ ] Supabase で無料プロジェクトを1つ作る（名前の例: `nicomaru-demo`、リージョン: Tokyo）
- [ ] マイグレーションを流す: `npx supabase link --project-ref <ref>` → `npx supabase db push`
- [ ] `supabase/seed.sql` を SQL Editor で流す（式場・プラン種別・宿題テンプレート・リスクルール）
- [ ] Authentication → URL Configuration: Site URL と Redirect URLs にアプリの公開URLを入れる
- [ ] Authentication → Email Templates → Magic Link: `supabase/templates/magic_link.html` と同じ内容にする（`{{ .Token }}` を含める。#14）
- [ ] 2-3 の手順で模擬データを入れる

### 3-2. アプリの公開先

- [ ] 公開先の環境変数に `.env.example` のキーを設定する（LINE・Resend・Ollama は空のままでよい）
- [ ] 公開したら、GitHub の Settings → Variables に `APP_BASE_URL` を登録する
  （`keepalive.yml` が6時間ごとにアクセスし、無料プランの自動停止を防ぐ。未登録なら何もしない）
- [ ] 1章の「共有デモ環境の記録」を埋めて Pull Request にする

### 3-3. メールについて

Supabase 標準のメール送信は、プロジェクトのメンバー以外には送れず、回数制限もあります。
模擬データは `.test` 宛てなので、**共有デモ環境ではメールは届かない前提**で進めます。

- プランナーはパスワードでログインする。
- 新郎新婦は `--login-links` で出したリンクを使う。
- 初回登録の実演は、demo-05 の招待URL（`seed-demo` の出力）から行う。

### 3-4. 片付け

最終発表が終わったら、Supabase プロジェクトとアプリの公開先を削除し、GitHub の `APP_BASE_URL` を消します。
削除前に、残したいスクリーンショットがあれば撮っておきます。

## 4. 共有デモ環境は要るか

学校での見せ方・検証のしかたで決めます。**迷ったら作らない**（ローカルで足りる）。

| 見せ方・検証のしかた | 必要な環境 |
| --- | --- |
| 発表者のPCを会場のプロジェクタにつないでデモする | ① ローカルだけで足りる |
| 録画した動画・スクリーンショットで発表する | ① ローカルだけで足りる |
| 先生が後日、自分のPCから触って評価する | ③ が要る |
| 発表中に、来場者や先生のスマートフォンで新郎新婦画面を操作してもらう | ③ が要る |
| チームの別メンバーが、Docker を入れずに画面だけ確認したい | ③ があると便利（必須ではない） |

作る場合も**1つだけ**です。「デモ用」「テスト用」を分けたクラウド環境は作りません。
試験（テスト）は ① と ② で行い、③ には試験で作ったデータを入れないでください（発表直前に `demo:reset` 相当で入れ直せる状態を保つ）。

## 5. 担当の分け方

実際の担当者はチームで決めます（#23）。

| 担当 | やること |
| --- | --- |
| ユーザー／環境担当 | 4章の判断、3章の準備（作る場合）、鍵の受け渡し、1章の記録の更新、発表後の片付け |
| メンバー | 2-2 の手順で自分のPCに模擬データを入れ、下のチェックが通るか確かめる。おかしければ Issue に書く |

### 環境確認チェック（メンバー）

`npm run demo:reset` のあと:

- [ ] プランナーでログインでき、案件一覧に模擬データの案件が5件出る
- [ ] 案件一覧で demo-01 のリスクが「高」になっている（リスクの再計算をした場合）
- [ ] 提出物一覧に「確認待ち」が出る（demo-01・02・03）
- [ ] demo-02 の BGMリクエストが「不備あり」で、指摘コメントが見える
- [ ] `demo-02-groom@demo.nicomaru.test` でログインし、自分の案件だけが見える
- [ ] demo-05 の招待URLを開き、初回登録ができる（Mailpit にコードが届く）
